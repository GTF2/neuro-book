# V7 小说记忆系统需求

状态：2026-09-09 需求讨论记录，开发者已要求同步落盘。已明确到可以开始 V7 模型设计；不是已定案的 schema、pipeline、产品 Spec 或实现完成声明。

## 1. 目标与设计起点

为整本小说建立可查询、可持续整理的记忆图与索引，让 Agent 能利用已经组织好的知识理解小说，而不必每次仅靠 shell 搜索和从头阅读原文。

V7 从需求重新设计，不要求兼容或延续 V6 的数据结构。旧版关于语义记忆、情节记忆和认识论的设计是参考基础，不因重新设计而全部作废；旧版具体类型、字段、约束和执行流程不自动成为 V7 的要求。V6 前 20 章数据是分析与设计推演材料，不是 V7 的架构约束。

## 2. 系统与 Agent 的职责

| 角色 | 职责 |
| --- | --- |
| 小说记忆系统 | 建立并整理记忆图与索引；处理跨章语义和实体归并；提供知识、情节及原文的查询能力。 |
| 使用系统的 Agent | 理解用户问题、决定是否追问、选择和组合查询、判断是否需要原文、推理并组织最终答案。 |

系统内部可以有 Agent，也可以通过 MCP 向外部 Agent 暴露能力。MCP 的工具列表与参数尚未设计，本轮不据此开始实现服务。

不把特定交互流程固化为系统要求。例如，“先给通用 if 线资料包，再询问改写点”只是讨论过的交互设想，不是系统合同。下列八个问题是下游使用场景，不是八条固定工作流。

## 3. 预期使用场景

开发者希望系统完成后，Agent 能借助它处理以下问题。需求面向整本书，当前 20 章样本不能证明全书能力已经实现。

| 编号 | 开发者的问题 | 对记忆与查询能力的要求 |
| --- | --- | --- |
| 1 | 这本书主要讲了什么？ | 支持形成整体认识，找到故事前提、主要人物、核心冲突和主线，不只是堆叠零散记录。 |
| 2 | 用一千字给我概括这本书的剧情 | 支持跨章梳理发展过程、主要因果和转折，由 Agent 按篇幅组织剧情概括。 |
| 3 | 列出苏天晴的人物关系网 | 统一同一人物的跨章身份与称呼，直接查询实际关系及其依据；不能把共同出现当成人物关系。图中信息足够时，无须读取原文。 |
| 4 | 介绍一下这个世界观 | 汇集散落各章的环境、种族、组织及世界规则，支持连贯介绍，而不只是名词清单。 |
| 5 | 介绍一下这个世界观的力量体系 | 汇集力量来源、获得方式、能力差异、成长、代价与限制等相关材料，不把系统补充的常识当成原作设定。 |
| 6 | 这本书有哪些势力 | 支持组织、阵营及其成员和关系的集合查询，不能把少量相关搜索命中冒充完整清单。 |
| 7 | 南嘉鱼和苏天晴是怎么认识的 | 找到并关联跨章相识场景、行动和上下文，支持解释过程，而不只返回一个关系标签。 |
| 8 | 如果要从第九章开始写一个 if 线，给我总结一下我需要的资料 | 支持 Agent 围绕分叉点查询人物、关系、状态、此前情节和相关设定；资料范围与交互方式由 Agent 按任务决定。系统不预设资料模板，也不默认负责生成 if 线正文。 |

### if 线的信息范围

开发者明确：可以使用全书信息，不限于分叉点之前已经向读者披露的内容。

设计需要支持区分以下信息，避免查询和使用时混淆；具体表示方式待设计：

- 分叉前已经成立、但后文才揭晓的事实。
- 人物在分叉时实际知道的事情；系统知道秘密不等于角色知道。
- 原作在分叉后的发展；可以参考，不是 if 线必然发生的未来。

这不等于已经决定其它查询都必须使用全书信息，也不把旧版防剧透的阅读位置过滤强制套到所有场景。一般查询中的阅读位置、故事时间及人物视角参数仍待设计。

## 4. 两类知识与依据

### 4.1 语义知识

系统应形成可以独立查询和复用的认识，例如实体身份、人物关系、所属势力、属性与世界规则。“苏天晴与南嘉鱼是朋友”属于 Fact，而不是只能留给查询 Agent 当场猜测的内容。

Fact 在此指有依据的命题，不意味着绝对正确的世界真相。它可以由原文支持，也可以由多条 Fact 或多条披露推断得出；不要求每条 Fact 都能对应一句直接明示它的原文。

### 4.2 情节知识

系统应保留具体场景、行动、过程及其上下文，支持查询“发生了什么”“怎么发生的”。情节知识不是语义知识的附属证据库，本身就是剧情检索对象。

同一段小说可以同时贡献语义与情节知识，不必二选一。Beat、披露和原文提供的材料应能与实体、关系及情节关联；是否保留旧版节点名称、如何划分情节记录和跨章事件，尚未定案。

### 4.3 披露与推断依据

需要区分命题本身、文本在具体位置表达的内容，以及系统依据这些材料形成的判断。叙述者描述、角色说法和系统推断不能被抹平成同一种无条件事实。

知识依据可以指向原文，也可以指向支持它的 Fact、披露及相关情节。查询应能取得这些依据，但不要求每次回答都展开完整推导链或逐条读取原文。

旧 V4 “读者推断不能作为其他推断的支持”的限制不自动继承。V7 应容纳有依据的推导链；怎样处理循环支持、重复证据和前提变化，是待解决的设计问题，而不是用禁止推断来回避。

## 5. 跨章整理与持续修正

跨章语义整理和实体归并是建图系统的核心职责，不交给每次查询的 Agent 从头重做。

- 同一对象在不同章节、名字、别称和身份下的材料应能汇集到一起；不能仅凭同名强制合并。
- 人物关系等语义内容应经过整理，不能只有概念与披露的共现连接。
- 新章节和后文揭晓应能改善此前的身份归并、关系与解释，不把逐章抽取结果永久冻结。
- 整理后仍需保留材料与依据，能够处理关系变化、来源分歧和错误判断；不是将旧说法无痕覆盖成一个结论。

“持续整理”描述系统能力，不预设固定调度方式。开发者提出的三个处理时机都保留为设计选项，并不互斥：

| 时机 | 可以承担的工作 | 当前状态 |
| --- | --- | --- |
| 章级 ingest | 读取新章时复用或归并实体，同时处理关系。 | 候选分工，未定案。 |
| pipeline 后续环节 | 先形成局部记录，再集中进行跨章整合。 | 候选分工，未定案。 |
| 梦境阶段 | 回访已有记忆、优化关系和归并，并依据多条 Fact／披露形成新的 Fact。 | 开发者提出的重要方向；是否作为独立阶段、何时触发及其修改权限未定案。 |

梦境不只是去重，也包含知识整合与推断；不能将模型自行重复表述视为新增原文证据。

## 6. 查询与原文的关系

记忆图不是原文的替代品，但读取原文也不是每次回答的必经步骤。

- 图中的知识足够时，Agent 可以直接使用图回答，例如人物关系网。
- 披露和 Beat 也是可直接利用的材料，不是只能跳转原文的指针。
- 图结构及已有记录不好解决的问题，允许 Agent 继续读取原文和上下文，由 Agent 判断是否需要。

系统鼓励使用原文的含义是提供方便、准确的原文访问路径，不是强制每条结论重新回原文核验。查询未命中也不能直接等价于原作不存在该信息。

## 7. V6 的已观察证据与结论边界

以下统计与样例来自本次对 [真实 V6 数据集](../t02-novel-memory-model-design/dataset-v6.json) 的只读分析，不是 V7 的质量承诺：

- 20 章、1942 段，177 条概念记录、274 条披露、409 条 Beat。
- 标签“苏天晴”有 18 条概念记录，“风信子”13 条，“南嘉鱼”9 条。这是同名记录数，不是独立人物数，也不是正文提及次数。
- 第 8 章末尾的 Beat 记录猫女请求坐在苏天晴旁边、苏天晴递便签；第 9 章第 3–18 段原文接续交友纸条、答应交朋友、添加好友与互报姓名。
- 第 9 章只有 4 条披露，其中两条分别记录南嘉鱼手足无措和苏天晴自我介绍，另两条是道具说明；Beat 与原文保留了比这些披露更完整的相识过程。

开发者已明确 V6 没有做实体归并，因此同名重复不是需要本轮修复的异常。该样例说明单纯归并身份不会自动补齐关系和情节，也说明不同记忆材料各有用途；不能据此推导“所有回答都必须读原文”。本次没有完成逐章语义质量审计或八类问题的端到端问答评测。

## 8. 尚待设计，不再作为基本需求反复询问

1. **知识表示**：实体、Fact、关系、披露、Beat、情节和原文之间的身份与连接方式；类型体系与表示粒度。
2. **整合机制**：跨章实体归并、关系整理，以及分散设定、跨章延续或回述情节如何关联。
3. **修正机制**：误合并与拆分、冲突、多来源支持、推导链和前提变化后的重审。
4. **查询合同**：可执行的查询、结果内容、分页与覆盖范围，以及阅读位置、故事时间和人物视角如何表达。
5. **执行分工**：ingest、后续整理与梦境的职责、触发时机和结果可用边界。
6. **验证方式**：用实际材料走通形成、查询和修正；以八类下游问题检验有用性，不以节点数或结构校验通过代替问答质量。成本、延迟及质量阈值尚未定量。

下一步先设计记忆内容及其关系，结合 V6 材料推演，再决定 pipeline；本文不选定数据库、TypeScript／JSON 表示、固定谓词、工具签名或交互模板。
