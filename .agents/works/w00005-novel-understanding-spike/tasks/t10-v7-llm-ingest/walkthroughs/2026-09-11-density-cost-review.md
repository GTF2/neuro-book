精简 A 少了一些局部指称和提及，但 Beat 没有减少，Disclosure 只少 3 条；首次 B 的命题、谓词和获知记录也没有随之减少。A 材料在 B 输入中的序列化长度从 9,081 降到 8,785 个 UTF-16 字符，只少 **3.26%**。这些字符数用来观察结构尺寸，不是 token 数或金额估算。

因此，本次追加的粒度提示没有显著改变主要建模密度。不能据此宣称精简思想无效，也不能把“提示词要求少建模”当成已经完成减量。

精简首章 B 的失败链可在 `evidences/density-sparse-001/ch01/round-1/integration/attempt-{1..6}/failed.json` 复查：

1. 首次候选使用 schema 不接受的 Episode 关系 `after`。
2. 补丁响应 JSON 无法解析。
3. 补丁合成后仍有原先的关系枚举错误。
4. 关系问题通过后，校验继续发现 5 个 Entity ID 与 A 的 Referent ID 重复。
5. 模型报告修复需要统一改名及更新引用，超出仅替换既有 ID 记录的补丁边界，请求完整重建。
6. 完整重建仍有 3 处可用时间依赖错误；例如 1:7 的时间约束引用到 1:15 才可用的时间记录。

这些失败触及枚举、命名、记录依赖和时间边界；不能归因为“事实太多”一个因素。前几个校验错误修正后显露出后续错误，也不表示后面的错误全由补丁新引入。

## 输入重复与长篇上下文

基线第一轮请求中，B 同时接收原文与 A 材料，C 再接收原文、A 材料、B 候选和逐项复核单元。第二章开始还加入接近预算上限的旧知识。

| 基线首次请求的字段尺寸，UTF-16 字符 | 第 1 章 | 第 2 章 | 第 3 章 |
| --- | ---: | ---: | ---: |
| 当前原文 `paragraphs` | 4,080 | 4,539 | 5,013 |
| 旧知识 `context` | 72 | 87,426 | 89,562 |
| A 材料 `material` | 9,081 | 12,144 | 15,456 |
| B 候选 `integration`，供 C 使用 | 25,118 | 32,051 | 37,846 |

首章 `context=72` 是空上下文对象的序列化开销，选中旧记录为 0。第 2、3 章各已选中 150 条旧记录；观察到的第 4 章也是 150 条、85,632 字符。当前原文只有两千余字，前文很快占满约九万字符的输入预算。

已发布前 3 章全部调用的 user JSON 字段值累计尺寸中，旧知识占 **56.2%**，当前原文占 **5.2%**，A 材料占 **11.3%**，前次候选占 **12.2%**，供 C 使用的 B 候选占 **13.0%**。分母是字段值序列化长度之和，未含 system 和外层字段名；这不是 tokenizer 归因，更不是这些字段各占多少美元。

这给出两个不同的优化方向：

- 合并 A/B 可以减少一份独立 A 请求及 A 产物传入 B 的过程，但联合输出仍需提供后续校验和 C 所用的材料；不能把 A 的全部输出视作可删除。
- 改善旧知识选择、压缩重复的结构文本与前次候选载荷，可能更直接减轻 B/C 的输入和理解负担。当前预算有界可以防止输入无限增长，却不能证明长篇召回足够，也不能消除预算内的高额常数。

前 3 章最终快照累计 1,034 条记录，其中只有 30 个 Entity、91 条 Fact、53 条 KnowledgeAccess 和 7 条 Episode；另有 200 条 Mention、110 条 Disclosure、59 条 Beat、144 条 Argument、144 条 Assessment 等。节点总数包含定位、结构、复核和历史信息，不是同数量的独立用户知识。不能以“记录变多”替代查询收益。

## 是否值得尝试合并阶段

**值得做小范围受控实验，尚不支持直接替换主线。** 原因是当前 A/B 确实重复读取原文并传递大块结构材料，而这次精简提示基本没有压低这些材料。但收费证据同样显示，A 仅占已发布费用 15.2%；联合阶段如果仍生成同量材料、增加推理或结构返工，节省可能被抵消。

把所有 A 请求费用机械删除、假设 B/C 和修复完全不变，只得到一个占当前费用 15.2% 的账目上界演算，**不是合并可实现的节省预测**。合并还可能改变下游质量和重复费用，所以真实结果不被这个演算保证。

建议下一实验只改一个边界：用一次联合抽取返回既有 A/B 草稿，仍由原有确定性校验检查完整结构，保留独立 C、现有 pending 和最多一次语义返工。不要同时新增质量节点、策略平台或更复杂的 schema，也不要修改 EntitySummary。用同一段连续章节、预先冻结的查询题目、相同模型及思考参数比较总费用、可回答且有证据的题目、补查需求、pending 损失与实际失败链；首章就失败的方案按失败报告，不与可用前缀比较“每章便宜多少”。

若联合方案仍被相同的 ID、时间和引用约束反复卡住，应优先分析模型输出合同里哪些字段确需语义判断、哪些只是可确定的结构负担。那是后续独立设计实验，不能通过静默放松现有校验来取得表面通过率。

已有 [thinking 对照](2026-09-11-thinking-cost.md) 在所测六份最终成功源请求上，关闭思考将输出减少 80.12%、同价口径费用减少 66.47%，但带来 B 结构失败，并漏掉拒绝样本中的真实语义问题。这个证据阻止直接给现有复杂流程关闭思考；它没有证明简化后的流程一定无法使用更便宜的模式。

已有 [语义返工价值复核](2026-09-11-semantic-rework-value.md) 同时发现了真错误修复和多轮意见摇摆。当前策略 -5 已落实最多一次返工，下一步应以可追溯查询效果评估保留的复杂度，不以 C 最终无意见或逐项通过率作为唯一质量目标。

这里没有“千万本书”的乘数。当前量级是单本长篇需数百至上千美元的模型费，值得继续优化；是否达到产品可接受价格，还缺目标用户付费、实际查询收益与更长样本的依据。

外推要求章节密度、模型输出与返工率近似不变，旧知识上下文持续有界，摘要只做局部更新，且单价与缓存假设成立。三章不能验证这些条件；完整 20 章也仍不能证明一千万字的检索召回和存储表现。尚未发布的第 4 章、开发对照实验和未知调用没有混入这个单位成本，相关费用在运行总账单列。

若把已发布前缀的 provider 累计 31.52 分钟同样线性放大，并假设单本完全串行、响应速度及修复率不变，约为 **31.7 天**。这只是当前流程的串行时间量级，不是厂商吞吐承诺，也不是用并发即可消除的全部等待：跨章增量整合依赖上一章已发布知识。

本次交付只形成截至时间的观察与下一实验建议，没有把 head=3 的基线或 head=0 的精简候选写成 20 章完成，也没有给精简候选虚构问答质量分数。
