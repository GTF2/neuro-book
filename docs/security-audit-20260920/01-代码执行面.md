## 1.1 项目 workspace 文件即代码（new Function 求值）— 严重

- **求值点**：`packages/neuro-book/server/agent/workflow/workflow-catalog.ts:123` —— 项目 `.nbook/agent/workflows/*/workflow.ts` 经 TS 转译后 `new Function(...)` 求值。`restrictedRequire`（:119）只拦截 `require`，`process`/`fetch`/`globalThis`/动态 `import()` 全部可达。
- **触发无审批**：`list()`/`get()` 即求值（:93 loadItem，项目源不缓存）。触发点包括 HTTP `GET /api/agent/workflow/catalog`（catalog.get.ts:25）、`list_workflows` 工具、以及 harness 打开/创建会话的路径（猎手定位 harness:3003/4046/5188，未逐行复核）。**打开一个恶意项目目录 = 静默执行其 workflow 顶层代码。**
- **写入通路**：workspace 写端点与 zip 项目导入（upload-project）按 containment 只限制在项目根内，**未见对 `.nbook` 系统目录的写入保留拦截**（两路猎手交叉确认；父代理复核 write.put.ts 无保留名规则）。zip-slip 本身防护到位，但把 `.nbook/agent/workflows/` 打包进合法 zip 即可投毒。
- **同类通路**：
  - `server/utils/runtime-artifact-import.ts:49` —— `new Function("specifier", "return import(specifier)")` 动态 import 编译产物（World Engine `calendar.ts`/`schema/index.ts`、profile/definition 编译链，编译来源同样是 workspace 内内容）。
  - 全仓 server 侧 `new Function` 共 3 处（本条 + codeact + runtime-artifact-import，父代理 rg 实测），无其他隐藏点。

**最小修复（按成本递进）**：
1. 止血：通用文件写端点与 zip 导入把 `.nbook/` 列为保留路径（改 `resolveContainedFilePath` 调用侧加保留段校验）。
2. 把 workflow/config 求值移入无网子进程，宿主只收数据。
3. 至少：项目源 workflow 首次加载要求用户审批，列表路径只解析元数据不执行顶层代码。

## 1.2 CodeAct 假沙箱可一行逃逸 — 严重

- `server/world-engine/codeact-sandbox.ts:77-103`：参数遮蔽只盖了 `Array/Object/String/Number/Boolean/Math/Date/JSON/console`，**未遮蔽 `Function`/`Reflect`/`globalThis`**；`(1).constructor.constructor('return process')()` 即逃逸。
- `checkAccess` 黑名单函数（:92）**定义后从未被调用**——死代码。
- 文件头注释（:15）作者自认："⚠️ 无法完全隔离全局对象（fetch / Bun / process 仍可访问）"。
- 入口 `execute_world` 是 Agent 工具（world-engine-tools.ts:41，code 为 LLM 输出），**无 `approvalRequired`**，非 writer profile 默认 readwrite（:92）。超时/结果大小限制只防资源滥用，不防逃逸。

**最小修复**：给 `execute_world` 补 `approvalRequired: true`（对齐 workflow-tools.ts:70 既有先例）；中期迁往真隔离（裸 vm 上下文或隔离子进程）。

## 1.3 bash 工具无审批无过滤，只读模式写审批被绕过 — 严重

- `server/agent/tools/file-tools.ts`：bash 工具（:367 起）接受任意命令，`bash -lc` 全量执行（:716-720 spawn），**无白名单/黑名单/危险模式检测，无 `approvalRequired`**。
- `mutatesWorkspace: true` 只标在 write/edit/apply_patch（:219/256/317），而只读模式写审批门按该标记判定（`server/agent/harness/neuro-agent-harness.ts:5549`，父代理复核）——**discuss/plan 只读模式下 bash 依旧免审批直跑**（残余未验证项：只读模式是否在工具集层就剔除了 bash，见 findings.json `readonly-mode-toolset-composition`）。
- cwd 有 containment（authorizeProcessCwd 限项目/工作区根），但只是起始目录，`cd /`、绝对路径无拦截。
- 子进程环境为 `{...process.env}` 全量展开（:664），宿主环境变量全部可见。

**最小修复**：给 bash 补 `mutatesWorkspace: true`（一行改动，使其进入只读审批体系）；只读模式从工具集剔除 bash 或强制审批；中期做环境变量白名单。

## 干净的部分（同类对照）

- **SQL 注入**：全参数化。唯一服务端 `$executeRawUnsafe`（database/locks.ts:11-15）的 key 经 `Math.trunc` 强制为数字，不可注入（风格建议改参数化，无漏洞）。nb-memory/nb-history 全部占位符绑定。

- **路径穿越**：防护体系完善且有专门测试（resolveContainedFilePath + assertRealPathContain ed 的 symlink/真实路径检查 + normalizeProjectRoot 保留名；zip 用 fflate 内存解包，每条目过 containment）。
- **原型污染**：全仓无自研递归 merge 工具；nb-workflow 用 `Object.create(null)` 且有 `__proto__` 防御测试。
