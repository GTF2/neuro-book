# 02 服务端注入面与访问控制

> 范围：packages/neuro-book/server（Nitro 路由、middleware、config、models、database、deploy、passport、agent HTTP 面）、prisma、nb-memory、nb-history。方式：源码级只读审计。
> 结论一句话：**传统注入类（SQL/命令/路径）防护相当好，真正的短板在"鉴权开关"和"用户可控出站请求（SSRF 面）"。**

## 2.1 访问控制

### 鉴权关闭 = 全站放行（要紧）

- `server/middleware/auth.ts:53`：`if (!isAuthEnabled()) return;` —— 全站守卫直接放行；`requireAdminAccess`（utils/auth.ts:181）同样短路。`isAuthEnabled()` 未配置时**开发环境默认关闭**（utils/auth.ts:29 注释，父代理复核）。
- `scripts/cli/source-dev.ts:85`：dev 默认绑定 `127.0.0.1`，但尊重 `HOST`/`NITRO_HOST` 环境变量覆盖。
- **危险组合**：非回环绑定 + 鉴权未开 = 局域网全权访问（读写小说数据、调 agent、进一步触达 01 号报告的代码执行面）。无启动期告警或阻止。
- 做得好的地方：恢复码导出在鉴权关闭时**硬拒绝**（passport/backup-keys/export.post.ts:16-18 返回 409）；shutdown 端点免 session 但有 loopback + 一次性 bearer token（randomBytes(32)）双门；登录有节流（login-security.ts，5 分钟封禁）。

**修复**：启动期校验"非回环绑定 + auth 未启用"→ 拒绝启动或显著告警。

### CSRF / cookie（可缓）

- 主应用 session cookie `sameSite: "lax"`（utils/auth.ts:21），无 CSRF token。Lax + 全 POST/JSON 的写面 = 跨站表单不带 cookie，当前可接受；属单点防线，建议补 Origin 校验。

## 2.2 SSRF：用户可控 provider baseURL（要紧偏低，设计内出站面）

- `server/api/config/models/provider-check.post.ts:482-510` 与 `provider-discover.post.ts:521`：请求体可带任意 `baseURL`/`proxy`/`apiKey`，服务端向该 URL 发起携带凭据的请求。embedding 同理（world-embedding.ts:84-89、subject-rag-index.ts:530-536）。
- **已有缓解（核实过）**：`credentialSource:"saved"` 时要求 id+baseURL+proxy 与已存配置完全一致（provider-credential.ts:21-35），**已存 key 不能被指到任意新 URL**；discover 有源站固定检查（origin 不符即拒）、`redirect: "error"`、超时与分页上限。
- **残余**：登录用户可让服务器对任意 URL（含内网/metadata 端点）发起 GET/模型调用，即经典 SSRF 探测。本地单机可接受；多用户/局域网部署需警惕。
- 干净的出站面：汇率（固定 Frankfurter）、passport 站（固定 URL）、shutdown（仅 loopback+一次性 token）。

## 2.3 敏感数据返回与错误处理

- 配置出站全部走 `maskSecret`（config-service.ts:1291-1303）：`{configured, maskedValue}`，掩码保留首4+尾4 —— 不是明文，但对短 key 泄漏 8 字符（可收紧）。写回有 `resolveSecretWrite` 契约（缺省保留旧值、`"cleared"` 显式清空），provider-credential 防按 ID 猜测串 key。
- provider 错误统一经 `provider-error-sanitizer.ts`（redactSensitiveText：api key/authorization/cookie/token/Bearer/sk-…/NBK1-… + 4000 字符截断）——**健康检查路径用了消毒器，但 `provider-discover.post.ts:523-529` 带 code 时回传上游错误原文未经消毒**（needs_validation：是否实际携带 key 取决于 adapter 是否把 key 放 URL query，见 findings.json）。
- 其余 handler 直接回传 `error.message` 的位置抽验均为本地校验文案或用户自身输入回显，未发现密钥/绝对路径泄漏。

## 2.4 上传面

- zip 项目导入：仅接受 `.zip`，`normalizeUploadPath` 拒绝绝对路径/`..`/空段，fflate 内存解包 + 每条目 containment —— zip-slip 防护到位。但见 01 号报告：**zip 可携带 `.nbook/` 投毒，这是当前未拦截的组合**。
- 封面上传：魔数 + MIME 一致性 + sharp 全量解码 + 64MP/20MiB 上限，错误信息不含 filename/bytes/物理路径——干净。
