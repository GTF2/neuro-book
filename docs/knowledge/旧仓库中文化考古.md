# 旧仓库中文化考古（服务第二批中文化）

> **对象**：`D:\MyProject\neuro-book失败fork开发但可以学习经验\neuro-book\`（1034 提交，全程只读未改动）。
> **目标**：当年 AI 底层把界面英文改中文**成功过**——挖出改动范围、实施方法、踩过的坑、效果与残留，为工程队第二批中文化（组件硬编码 + 技能描述 35-40 字限）提供先例与避坑清单。
> **日期**：2026-09-20。方法：git log 关键词检索 → 六个核心提交逐一 `show --stat` + diff 抽样 → HEAD 残留同口径扫描（与 `docs/knowledge/界面英文词表.md` 同一 grep 模式，可直接对比）。

## 一、结论速览

1. **方法 = i18n 词条为主，组件硬编码为辅清理**：双语 locale 文件（`app/i18n/locales/zh-CN.ts` + `en-US.ts`）承接绝大部分文案；组件里绕过 i18n 的硬编码（无论英文还是中文）都被视为待清理项。当前 fork 的 i18n 双语结构就是从旧仓继承的。
2. **改动范围 = 四层**：locale 词条层、组件渲染层、测试断言层、（文档站）locale 源层。**测试断言层是最容易被漏的第三层**。
3. **最大的坑不是编码，是"双向往返"**：中文化过程中 AI 曾把中文直接硬编码进组件（绕过 i18n），两周后专门提交收口回去；同时测试断言里写死的英文/中文 UI 文案成批失败要同步。**先定纪律再动手**是旧仓用返工换来的教训。
4. **效果有量化证据**：同口径扫描，旧仓 HEAD 模板文本节点英文残留 **69 条** vs 当前 fork **182 条**——清扫有效，但新功能持续带入新英文，中文化需要随功能走的护栏而不是一次性运动。

## 三、改动范围（哪些文件/层）

1. **locale 词条层**：`app/i18n/locales/zh-CN.ts` + `en-US.ts`。纪律：**每加一个 key 中英同步补齐**（`44eeb913` 一次 +137/+151 行）；zh 文件里填英文值（"假中文"）是清扫对象之一（`d5b225dc` 约 60 处）。
2. **组件渲染层**：模板文本节点、`label=`/`title=` 属性、确认框/错误消息的 fallback 字符串、菜单常量数组。涉及面最广（`d5b225dc` 24 个组件约 160 处：桌面菜单、diff 工具条、Agent 气泡、plot 分区标题、world-engine 工作台、RAG 面板、文件树悬停提示）。
3. **测试断言层**：源码文案断言（`expect(源码).toContain("界面文案")`）写死了 UI 字符串，中文化后成批失败——`020908bb` 同步 27 处。**这一层在 fork 的对应物是 world-engine 系的源码断言测试**（当前 fork 同样存在 `world-engine-*.test.ts` 源码断言模式）。
4. **文档/治理层**：`9eef8ab6` 把 README/文档站的中英 locale 源统一；另有 `cd109f7b` 把"回复与思考一律简体中文"写进治理语言硬规则（Agent 产出文案默认中文的源头）。

## 四、实施方法（怎么改的）

1. **组件接入 i18n 的标准动作**（`d5b225dc` diff 实证）：
   - `const {t} = useI18n();` 注入，字符串字面量换 `t("命名空间.key")`；
   - **静态常量数组里的文案要改成 `computed(() => ...)`**——DesktopTitleBar 菜单从 `const menus: readonly MenuGroup[] = [...]` 改为 `computed<readonly MenuGroup[]>(() => [...])`，否则语言不响应/SSR 期取值错误。第二批改 plot 面板的分区标题常量时会再遇到这个模式；
   - 确认框/错误 fallback（`confirm(...)`、`resolveApiErrorMessage(err, "默认话术")` 的第二参）同样 t() 化。
2. **zh/en 双语同步**：每次加 key 两个文件一起补（en 不是摆设，语言切换功能依赖它）；zh 里暂填英文的词条会在下一轮清扫被点名。
3. **不翻译的边界**（`3fe02077` 提交说明原文口径）：**`console.error`/日志保留中文或原文不进 i18n**——那是给开发者看的诊断输出，翻译没有收益反而破坏日志检索。第二批同样适用：API 报错原文透传保留，外壳说明中文化。
4. **悬停提示与无障碍标签一并扫**：文件树状态圆点 `title`、"请先打开项目"类提示都在清扫清单里——与当前词表"全局框架"组（Application menu/Minimize 等）同型。

## 六、效果与残留

- **效果**：`d5b225dc` 一轮清扫吃掉约 220 处（60 词条 + 160 组件）+ 悬停提示；`44eeb913` 再吃掉 Agent 面板一批。用户主链（书架/新建书/工作台/聊天）在旧仓后期截图里已基本全中文。
- **残留**：HEAD 同口径扫描仍有 **69 条**模板文本节点英文（当前 fork 为 **182 条**，词表已全量登记）。残留集中在：后加的 plot/workflow 预览工作台、world-engine 预览、开发者 preview 页——**与当前词表"剧情面板/世界引擎/开发者预览页"三组几乎逐条重合**（旧仓清扫也没啃完这三块硬骨头）。
- **技能描述中文化先例**：未找到"批量中文化技能描述"的专门提交；builtin profile 的 `manifest.name`/`description` 引入时即为中文（如"世界引擎""记忆整理"）。**描述限长是新要求**：现存 manifest.description 普遍 60-80 字（见附录两例），35-40 字限属于对现状的收紧，无旧例可抄，需按词表口径新写。

## 七、对第二批中文化的四条直接启示

1. **先立纪律再动手**（旧仓返工两周换来的）：所有替换走 `t()` + 双语同步，禁止组件内直接写中文；`console`/日志不翻；API 报错原文保留+中文外壳。
2. **把断言搜索列进完成定义**：改每个词条前先全仓 grep 旧字符串（含 `*.test.ts` 源码断言），命中即同步改——旧仓 27 处断言返工就是没提前搜。
3. **常量数组改 computed** 是隐性工作量，排量时给 plot 面板分区标题类改动按 1.5 倍估。
4. **攻击顺序抄旧仓**：先啃 zh 词条"假中文"（改一个文件，见效最快，对应词表第七/四组）→ 再清组件硬编码（词表五/六组）→ 开发者 preview 页不翻译只隔离。技能描述 35-40 字限是纯新写，按"一句职责+关键工具+边界"模板压缩（参考附录两条 40 字内示例写法）。

## 附录：builtin profile 品读（参谋部诚实未读清单遗项）

> 对象：`packages/neuro-book/assets/workspace/.nbook/agent/profiles/builtin/` 下两份 TSX profile（提示词正文内嵌于 `profileText` 模板）。服务单C 的"🪄 AI 整理按钮"与"世界面板打捞"设计。

### world.engine（世界引擎，144 行）

- **职责**：维护与验证当前 Project 的结构化世界运行态——subject 写入（首写自动创建）、slice（时间轴切面）写入、按时刻查询 reduce 后状态、反查引用（`findRefs`）与向量搜索（`search.text`）。只管 `world-engine/` 与 Project SQLite 的 World* 数据；**明确不接旧 simulation workflow**，不写正文、不做剧情结构设计。
- **工具**：文件四件套（read/write/edit/applyPatch）+ agent 自省两个 + 核心是 **`execute_world("readwrite")`**——CodeAct 沙盒里一段 JS 同时完成查询、写入、精确修改、删除（`world.subject.*` / `world.slice.*` / `world.time.*` API 族）。
- **与落库审查的接口（单C"世界面板打捞"直接可用）**：`execute_world` 统一返回 **`{data, issues}`**，issues 按 severity 分级——`error`=数据错误必须修正；`advisory`=补过去/覆盖关系的语义提醒，**不自动回滚但要向用户确认是否符合剧情**。这就是"拍板落库"时机器侧审查的现成挂点：面板打捞出的任何回写都应走这个通道并展示 issues，解释时用返回的 `title/message/explanation`，不抛内部 code。展示面数据 API：`world.slice.list({withPatches:true, subjectIds:[...]})`、`subject.get({deref:true})`。
- **值得注意的边界**：删除是物理删除不可恢复（仅限剧情回退/作废/清误）；同一时间点只允许一个 slice，补丁走 `slice.editPatches`；时间一律项目日历字符串（`world.time.parse("公元2020年4月12日 18:00")`），禁止裸 instant。

### memory.curator（记忆整理，92 行）

- **职责**：不扮演角色、不写正文，只维护**单个 subject 的"当前稳定认知集合"**（memory.jsonl 的 `SubjectMemory[]`：`topic`/`aliases?`/`view`）。输入三件：subjectPath + 本轮新增 facts + 当前 memories。
- **工具**：**只有 `report_result` 一个**（受 OutputSchema 约束）——它是纯决策器：产出 JSON Patch，**由工具层校验并写回**，自身无文件/世界写权限。这个"出 patch 不落盘"的结构对按钮类功能极其友好。
- **与落库审查的接口（单C"🪄 AI 整理按钮"即插即用）**：输出即 `patch`（应用到 currentMemories 的 JSON Patch，无需更新返回空数组），工具层校验后写回——按钮只需调用本 profile → 展示 patch 摘要（`report_result.result` 是人类可读的增/并/删说明）→ 确认后由既有工具层落盘。内置审查规则两条可直接搬进 UI 文案：①**外部信息隔离**——"真实隐藏设定/上级裁决/作者知道"类 facts，只有角色已被告知、亲眼所见或能自然推断时才可入 memory（防剧透泄漏给角色认知）；②**认知合并**——"粉色头发的女孩子=艾琳娜"这类合并要并 topic 且旧称留 `aliases`，合并时保留旧 view 中的稳定认知。
- **描述限长现状提醒**：两份 manifest.description 分别约 70/40 字，均超或贴线 35-40 字限（世界引擎条明显超），第二批收紧描述时以这两份正文为素材压缩，勿凭空写。
