## 1. T0.1 写后结算表协议（01900a91）

### 行为规格

writer 每章写完，在 `report_result.result` 文本末尾追加固定格式 markdown 块，三节：`### 新增事实`（条目带 `[人物]/[物品]/[状态]/[时间]` 类别标签）、`### 与既有设定的冲突点`、`### 未确定项`；空节规范写法 `- 无`。leader 写后评审优先消费结算块，未覆盖或旧会话无块时才回读正文。协议定义与解析收敛在 `server/agent/profiles/writer-settlement.ts`（114 行）单一事实源。

**接口形状**：
- 常量：`CHAPTER_SETTLEMENT_HEADING = "## 本章结算"` 及三个小节标题常量。
- `parseChapterSettlement(text) → { kind: "missing" } | { kind: "present"; settlement: ChapterSettlement; raw: string }`；`ChapterSettlement = { newFacts: string[]; conflicts: string[]; unresolved: string[] }`。
- 协议样例（writer profile 规定格式）：新增事实节条目如 `- [人物] 莉雅首次登场，与薇洛丝在星陨遗迹相遇`。

**关键设计决策**：
1. **文本协议而非 tool call**（决策 D1，三条理由）：mock LLM 不支持 tool_calls 所以 e2e 可锁；writer 工具面不加新工具（只读边界不动）；leader 在会话流里直接消费，无新管线。
2. **missing ≠ 无事实**：判别联合区分「没按协议输出」与「输出且为空」——missing 必须退回重读正文的旧评审路径，绝不能把没找到当成没有新事实。
3. **宽松解析不抛错**：主标题行首锚定 `/^#{2}\s*本章结算\s*$/`（正文提到字样但无标题格式不算）；条目允许 `-`/`*` 前缀与缩进；`- 无` 解析为空数组；未知小节标题后内容静默忽略；块在下一个一/二级标题处终止。
4. **宪法兼容声明写进提示词并被测试逐字锁定**：「事后上报」「不是写作前置条件」两个短语在契约测试中断言存在。
5. **leader 处置细则**：未确定项「逐条向用户确认或显式挂起，不要默认入 canon」。

**测试如何锁**：契约测试 4 条——①真实执行 `writerProfile.prepare()` 拿 systemPrompt，断言四个常量、四个类别标签、「事后上报」「- 无」逐字出现（**锁提示词与解析器同源**）；②三节齐全可解析+「- 无」→`[]`；③向后兼容（无块→missing，含空串）；④边界（下一二级标题终止、行尾空白可识别）。e2e 1 条：mock 吐固定样例→会话落盘→**从 session recovery API 取消息原文**（DOM 渲染吃 markdown 标记，不能从气泡取）→用生产解析器断言三节结构。

## 2. T0.2 定稿原子提交（83ba2198）

### 行为规格

`finalizeChapter` 把三步写入组织成**补偿事务**：检查点（读正文现状，正文写入走 nb-history 记账，before/after 快照即持久检查点）→ 正文 → World 切面逐条 writeSlice → Promise beat 逐条 upsert → 落 committed 事件返回结算凭据；任一步失败**逆序补偿**（beats→slices→正文），落 rolled-back 事件并抛错；补偿自身失败逐项记入 `rollbackFailures` 显式上报，绝不静默。

**接口形状**：
- API：`POST /api/projects/plot/finalize?projectRoot=<name>`。body：`chapterPath`（1-1024 字符相对路径）、`content`（正文全文）、`worldSlices[]`（≤64：`instant` 为**数字字符串**——JSON 承载不了 bigint，`title?/summary?/kind?`、`patches[]`（1-64 条：`subjectId/op(replace|increment|remove|append)/path/value?/summary?/type?/name?`））、`promiseBeats[]`（≤64：`promiseId/sceneId/kind(plant|advance|setback|payoff)/note?`，note 三态：undefined=沿用、null=显式清空）。
- 成功响应：`{ status: "committed"; chapterPath; chapterContentHash(sha256); chapterBeforeHash|null; worldSliceIds[]; promiseBeats[] }`。
- 失败：HTTP 500 `{ code: "CHAPTER_FINALIZE_FAILED"; step: "prose"|"world"|"promise-beat"; rollbackFailures: string[] }`——**rollbackFailures 空=已完全回滚可安全重试；非空=有残留需人工介入**。
- 端口 `ChapterFinalizePorts` 9 个成员（readChapterFile/writeChapterFile/deleteChapterFile/writeWorldSlice/deleteWorldSlice/findPromiseBeat/setPromiseBeat/removePromiseBeat/appendEvent），`createChapterFinalizePorts` 负责真实装配。
- 事件 JSONL：`<projectRoot>/.nbook/chapter-finalize-events.jsonl`，记录 `{ type: "chapter-finalize.committed"|"chapter-finalize.rolled-back"; occurredAt; chapterPath; chapterContentHash; chapterBeforeHash; worldSliceIds; promiseBeats; failure?; rollbackFailures? }`。

**关键设计决策**：
1. **World 侧只支持新增切面**：只走 writeSlice——头注释明说「editSlice 的逆操作无法用公开 API 精确表达」，编辑既有切面留在原子单元之外。
2. **补偿事务而非 DB 事务**：文件系统、project.sqlite world 表、plot 表三存储无共享事务边界；回滚失败显式上报不静默。
3. **JSONL 事件而非 Prisma schema**：避免「并发生成 Prisma client 的已知崩溃风险」。
4. **开发中自抓的真 bug**：writeSlice **先提交再返回 issues**——error 级 issue 须**先把 sliceId 记入回滚清单再判失败**，否则回滚会漏删已入库切面。已加变体用例锁住。
5. 检查点读取在 try 之外（零副作用阶段失败直接抛）；回滚正文幂等跳过（`current === before` 不写，`before === null` 删文件）；单项补偿失败不中断其余补偿；事件落账失败刻意吞掉（保原始错误透传，缺行靠对账补）；超限校验（64/64）在进入流程前抛（零副作用）。
6. 归因区分：正常写入用 `USER_LOCAL_ACTOR`，回滚补偿用固定 `{kind:"system", source:"chapter-finalize"}`——nb-history 里可区分。

**测试如何锁**：7 条单测全用内存端口：第二步失败全量回滚（正文写回序列 `[NEW, BEFORE]` 锁补偿确实发生）；**error-issue 不抛异常变体**（锁真 bug）；第三步失败既有 beat 恢复原值（锁先捕获 previous 再 upsert）；提交前文件不存在→回滚删除新建文件；成功路径结算凭据与三处写入一致+恰好 1 条 committed 事件；补偿自身失败上报（`rollbackFailures[0]` 同时含对象标识与原因）；JSONL append-only 逐行可解析。

- 【现成】`server/world-engine/world-engine.facade.ts:109` `writeSlice` 已存在且包了 `runInTransaction`；issues 语义与新库 world.engine profile 的 `{data, issues}`（severity error/advisory）同源——T0.2 的「error 级 issue 视为失败」判断直接对得上。`shared/dto/plot.dto.ts:311` beatStats 已在，promise 体系同形。

## 3. T0.3 设定检索自动候选（609adc00）

### 行为规格

leader 专用只读工具 `retrieval_candidates`：编译 brief 前对 `lorebook/` 节点（frontmatter 的 title/summary/trigger/entryType/status）与 `manuscript/` 正文做**确定性词元匹配**（CJK bigram+拉丁词），产出结构化候选清单给用户逐项确认；确认结果经 `resolveConfirmedLorebookEntries` 收口为纯 path 数组——与 writer handoff 的 `context.lorebookEntries` 完全同形，**writer 协议零改动**。

**接口形状**：
- 工具入参：`query`（必填）、`includeManuscript?`（默认 true）、`limit?`（1-30，默认 12；正文片段上限为 `floor(limit/2)`）。
- 候选 DTO：`candidateId`（`lb-N`/`ms-N` 组内连续）、`source`（lorebook-entry|manuscript-fragment）、`path`（lorebook 为目录路径带尾 `/`，正文为 `.md`）、`title`、`summary`（200 字符有界）、`relevance`（=命中词元数/查询词元数，(0,1]）、`matchedTerms[]`、`risk`（frontmatter 解析失败/status≠active 等）、`excerpt/excerptLine`（仅正文，240 字符有界）。
- 确认协议双通道：`{ candidateIds?: string[]; paths?: string[] }` → 返回 `{ lorebookEntries: string[]; rejected: Array<{value; reason}> }`。
- **两种错误两种处理**：未知 `candidateId` 直接抛错（调用方协议错误，防漂移）；非法 `path` 逐项进 `rejected` 带原因（用户输入错误，不整体失败）。路径校验拒绝：空、盘符/前导 `/`、`workspace/` 前缀（跨项目）、含 `..`。

**关键设计决策**：
1. **确定性匹配而非 embedding**：可单测、不依赖配置；语义深度判断留给 retrieval 子代理（清单不够再派，其结果同样先经用户确认）。
2. **只读零审批**：read admission 复用 `authorizeFileOperation(context, root, "read")`，与 file tool 同一授权边界，discuss/plan 模式也能跑。
3. **判断字段不带给 writer**：相关性/摘要/风险止步于清单层——「writer 动笔前上下文只含事实不含意义」，由 prompt 断言锁死。
4. **可复现**：candidateId 稳定编号+确定性排序（relevance 降序、同分 path 中文 locale 升序）。
5. 有界防护：摘要 200/节选 240/查询词 16/候选 30/单文件 2MB（超大跳过且不计入扫描数）。

**测试如何锁**：12 条工具单测（临时目录夹具）：分词边界（`"莉雅 封印之匙, seal!"` → `["莉雅","封印","印之","之匙","seal"]`；单字拉丁不成词、单字 CJK run 保留）；清单结构稳定（编号格式/单行摘要/排序）；`retrieval.enabled=false` 排除；risk 标注；无命中带引导 note；limit 生效与截断；确认去重保序；未知 ID 抛错；手填路径穿越/绝对/跨项目全进 rejected；渲染双形态；工具定义契约。契约测试 3 条锁 leader prompt（「确认后才放行」「判断字段不带给 writer」）。

## 4. T0.4 全稿扫描后端（8a1b001b）

### 行为规格

llmlint-check API 的目录目标从 400 拒绝改为调 `runLlmlintScan`：spawn `bun <skillRoot>/bin/llmlint.ts check <目录> --format json`，CLI 递归收集全部 `.md/.markdown/.txt`，服务端归一化为 `kind: "check-scan"` 聚合报告。单文件路径行为零改动。全程只读。

**接口形状**：
- `runLlmlintScan(input)` 入参：`skillRoot/absoluteDirPath/review/minLevel/scanAll/topIssuesLimit/timeoutMs`（默认 300s vs 单文件 60s）+ `bunBinary/execFileImpl` 测试注入缝。
- `ProseLintScanResult`：`fileCount/filesWithIssues`、`summary{total,high,medium,low,visibleChars}`（级别维度+总字数）、`filter`、`registry{rulesets,totalRules,activeRules,disabledRules}`、`files[]`（文件维度全量：`{filePath,relativePath,total,high,medium,low,visibleChars}`，total 降序）、`rules[]`（规则维度全量：`{ruleId,ruleTitle,namespace,level,review,count,fileCount}`，count 降序）、`topIssues[]`（级别→filePath→line→column 排序；**默认 20/上限 200/0=不要**）、`durationMs`。
- HTTP 语义：200 聚合结果；400 校验失败；502 CLI 失败；503 skill 不可用。

**关键设计决策**：
1. **复用 CLI 目录展开不自研递归**：延续「只 spawn 不 import」边界。
2. **单/多文件双形态归一化**：CLI 对只剩一个文件的目录输出单文件 `check` 形态而非 `check-multi`——不归一化就会出现「扫到只剩一章的目录就 502」边角假红。
3. **退出码不当成败信号**：llmlint 是 eslint 式门禁，有 high 命中即 exit 1——只看 stdout JSON 是否可解析。
4. **top 命中有界但两维度给全量计数**：3936 条命中不全量回传，UI 下钻靠 files/rules 维度的全量计数。
5. 真稿基线（当时实测）：236 文件 1433ms、3936 命中×91 规则、可见字 811,985。

**测试如何锁**：6 条 runner 单测：check-multi 归一化主用例（三维统计精确断言）；topIssuesLimit 有界语义（1/0/9999→clamp）；**单文件退化形态归一化**（直接锁「只剩一章的目录不 502」）；`kind:"fix"` 抛错（形态白名单）；stdout 前后噪声仍可截取 JSON；真实 CLI 目录扫描（三维自洽 Σfiles===Σrules===summary.total + **扫描前后文件逐字节不变**的只读保证）。

### 新库落地建议

## 5. T0.5 worldAnchor 半自动补齐（bc48f32a）

### 行为规格

Scene 的 worldAnchor（开始/结束时间、出场 subjects、地点）存量老项目往往缺失。本件实现半自动补齐：后端**纯词面匹配**（不调 LLM）扫每章正文，从 World subject 与有效 lorebook 条目识别候选角色/地点，生成**只写 pending 队列**的建议，绝不直接写 Scene；人工经 confirm/reject API 取舍。确认时，一条建议覆盖的该章全部活动 Scene 在**单个 SQLite 事务内合并式写入**（字段级首写保护：只补缺失，保留已有时间/地点/subjects）。真稿验收：222 pending/2 跳过/0 失败（1882ms），20 章样本 87 候选词 87/87 在原文命中——并明确该准确率**只代表词面出现**（被回忆/谈及也会成候选），这正是全部保持 pending 的原因。

**接口形状**：
- 四条路由（挂 catch-all，前缀 `/api/projects/plot`）：`GET /world-anchor-suggestions`、`POST .../generate`、`POST .../confirm`、`POST .../reject`；confirm/reject body `{ suggestionIds: string[] }`（1-100 条、每条≤160 字符、去重），**路由层 maxBytes 16KB**。
- 建议 DTO：`suggestionId`（`was-<seq>`）、章节三元组、`sceneCount`、`subjectIds`（≤100）、`locationSubjectId?`、`timeEstimate?{startInstant(数字字符串), reason}`、`evidence[]`（`{subjectId,name,type,occurrences,resolved,source(world-subject|lorebook)}`）、`note?`、`status(pending|applying|confirmed|rejected)`、时间戳。队列落 `.nbook/world-anchor-suggestions.json`（version `world-anchor-suggestions-v1`）。
- confirm 返回逐条 outcome：`{ suggestionId, status: confirmed|skipped|failed, reason?, appliedScenes[] }`（`startInstantApplied` 仅当该 Scene 原本为 null 才非空——报告的是「本次实际写入」）。

**关键设计决策**：
1. **词面门槛**：单字名排除；2 字名需正文出现≥2 次；≥3 字 1 次即可；停用表 `{"世界"}`；括号别名拆分（「芥末（郭紫莉）」）取出现次数最高的最佳别名。
2. **候选注册表双源、World 优先**：lorebook 只收 active、无 frontmatter 错误的 character/location；同 basename 重名目录判 ambiguous 不进自动建议，只在 note 提示人工——避免把两个不同设定写进同一 unresolved subject。
3. **状态机 pending→applying→confirmed 实现崩溃恢复**：确认前先落 applying；Scene 事务失败回退 pending（可重试）；**Scene 已提交但 confirmed 队列写失败则保留 applying**——下次确认因合并是「只补缺失」天然幂等，可安全收口，不伪造状态。确认时还重读 store 校验状态未被并发改变（防御纵深）。
4. **每条建议独立事务**，单条失败不影响其余；**并发双层防护**：facade 内 promise 链串行单进程 + proper-lockfile 项目锁（stale 30s）跨进程；读队列裸读不加锁。
5. **存量正文三级回退，宁 failed 不猜测**：frontmatter 指针→结构化目录键→标题唯一精确匹配；同标题无结构化键时 failed++ 拒绝关联；**从不回写正文 frontmatter**。
6. 证据只取 markdown body（frontmatter 名字不算出场证据）；时间估计是**继承不是推断**（沿用前章已确认锚点最晚时刻，reason 明写「仅供人工复核」）。

**测试如何锁**：服务 14 条+API 4 条（文件共 16）：词面门槛/注册表过滤/生成跳过与历史保留/标题消歧；**确认保留已有锚点只补缺失**（端到端：确认后 `GET scenes/:id` 断言 startInstant/endInstant 保留且只加了 subjects）；**applying 恢复协议**（Scene 已写但落盘失败→保持 applying→二次重试幂等收口）；事务失败回 pending；损坏 Scene 注入（libsql 直写坏 JSON）断言整体回滚且未污染；DTO 拒重复 ID 与非法状态；16KB 超体拒绝。验收 JSON 结构：`{schema, sourceProject, originalManuscriptDigestBefore/After(相同 SHA-256), originalManuscriptUnchanged: true, generated, skipped, failed, pendingSuggestions, sampleChapterCount, sampleCandidateCount, sampleEvidenceHitCount, sampleTitles}`——**原子性证据=摘要不变，证据质量=固定样本词面命中**。

### 新库落地建议

- 【现成】新库 `server/plot/services/` 已有 `scene-world-anchor-resolution.service.ts` + `scene-world-anchor.validator.ts`——**这是 Scene 锚点的解析/校验（另一回事），不是建议补齐**，但说明新库 Scene 锚点字段模型健在，合并写入的目标字段现成；`proper-lockfile` 4.1.2 已是 package.json 依赖（150 行），锁方案零新增。

## 7. T0.7 一致性审计（7a0e2f16）——审查流的服务端雏形

### 行为规格

定稿前对一章做**三源核对**：①承诺账本（该兑现的是否兑现）②World 写入证据（结算声明是否有凭据）③正文 llmlint（high 命中）——产出**成句中文**三段报告+三档建议。服务是确定性纯函数（ports 注入），绝不写数据、不自动改稿。

**接口形状**：
- `POST /api/projects/plot/consistency-audit`（独立路由文件，不进 catch-all；`maxBytes: 128KB`）。body：`chapterId`（`^\d+$`）、`settlementText`（max 100,000）、`prosePath`（trim，1-1024）、`finalizedWorldSliceIds[]`（≤64 条、去重）。
- 响应：`{ chapterId, title, subtitle, promise: {title, availability, ok, issues[]}, world: {同构}, text: {title, availability, ok, issues: {line, excerpt(20字), ruleName}[], summary}, advice }`——**title/subtitle/issues/advice 全是服务端拼好的成句中文**，前端不做二次拼接。
- ports 四个：`getChapter / listPromises / readWorldSliceIds / runLint`。

**关键设计决策**：
1. **三源各查什么**：承诺源——只筛 `open` + 期限章=本章 + `!beatStats.factual`（无兑现证据），产出「《{title}》到了该兑现的时候，这章没兑现。」；cadence 明确不参与硬判断。World 源——先解析 T0.1 结算块：缺块→`unavailable`；无事实→`ok`；有事实没给 sliceIds→`unknown`；凭据读不到→`unknown`。文字源——只投影 high 命中，按行号排序，摘录截 20 字（按码点截，避免代理对劈半）。
2. **不伪称审计能力**（本件灵魂）：核心注释「结算是自由文本，无法与 World Patch 做语义等价判断；因此状态对照只报告结构化写入证据是否可读取，**绝不声称自然语言事实已入账或漏记**」——三态 `ok/unknown/unavailable` 就是为此设计，宁可「不可核对」不冒充「通过/失败」。
3. **建议三档**：硬伤（promise issue）→「这章先别定……」；轻问题（high 命中或 world 不过）→「问题不大，改不改你定……」（不可核对只算轻）；全干净→「三样都过关。就差你一句话——定，还是再看看？」——**决定权始终留给作者**。
4. **POST 做查询**：body 含 10 万字符级结算文本；且独立文件避免扩大 Plot catch-all。
5. 调用方必须显式给 prosePath——「避免 chapter 关联多个正文时静默猜测」。

**测试如何锁**：服务 4 条：期限本章+无兑现→硬伤档原句；**凭据可读但结算为自由文本→锁 world 段完整输出为 unknown+「无法逐条核对」句（锁诚实性）**；缺结算块→unavailable；lint 投影（medium 滤掉/high 按行排/截断/ruleName 取 title/summary 成句）。API 1 条走真实模块锁装配。

### 新库落地建议

- 【现成】三源的挂点在新库全部成立：`parseChapterSettlement`（随 T0.1 建）、World 凭据读取（world-engine facade）、lint（随 T0.4 建）、`beatStats`（plot.dto.ts:311）、promise 枚举同形。
- 【须建】`server/consistency/` 目录（新库不存在）+ 独立路由 + route-map 登记（新库 `server/openapi/route-map.ts` 在）。

## 9. 跨件共性模式（第二批可直接抄的八条规矩）

1. **端口注入+纯函数 service**：service 只依赖 ports 接口，facade 负责真实装配（Prisma/World/文件系统）。单测全部用内存假端口，故障注入（锁失败/写失败/脏数据）全覆盖，不依赖真库。新库 plot 域分层（services/facade/repositories/contracts）与此完全同构，照常落位即可。
2. **显式失败上报，绝不静默**：补偿失败逐项进 `rollbackFailures`；confirm/reject 逐条 outcome（confirmed/skipped/failed+reason）+`missingSuggestionIds`；宁可上报残留也不假装干净。
3. **不伪称能力三态**：`ok / unknown / unavailable`——宁可报「不可核对」，不冒充「通过/失败」（T0.7 灵魂，审查流的信任基础）。
4. **有界防护前置**：body maxBytes（16KB/128KB）、条数上限（64/100/30）、字符截断（200/240/20 按码点）、超大文件跳过；超限校验放在零副作用阶段。
5. **协议常量唯一源+契约测试逐字锁**：提示词与解析器从同一组常量生成，契约测试真实执行 profile 拿 systemPrompt 断言逐字一致——防两处漂移。
6. **文案是服务端契约**：报告 DTO 直带成句中文，服务端拼装，前端不二次拼接；文案包先于服务定稿。
7. **幂等合并+状态机崩溃恢复**：写前落 applying、失败回退 pending、已写未登记保持 applying 靠幂等合并收口——跨多存储操作不怕中途崩。
8. **测试锁行为不锁实现**：正文写回序列、「未调用」断言（短路）、变体用例锁真 bug（error-issue 先提交）、只读保证（扫描前后逐字节不变）。
