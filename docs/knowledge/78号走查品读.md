## 二、主题发现

### 1. 填空地狱的病根找到了（命中我会弹药条 10，架构级背书）

Round 06 明确：`get_chapter_writer_brief` **是给 AI 用的只读聚合工具**——"返回 leader/director 可直接改写成 invoke_agent.message 的素材"、"不是自动写作大纲生成器"、status（ready/needs_plot/needs_world_anchor/needs_world_context）与 warnings 是给 **Agent 判断能不能写**的信号。**用户实测面对的 ChapterBrief 十几框填空弹窗，源头是 AI 工具接口被原样暴露给了人。**"做作业解题"批判从产品层追到架构层：不是功能错了，是接口的客户弄错了。009 的"AI 代填、人确认"不是逆架构改造，是**把接口还给 AI、回归设计本意**。

### 2. 强证据验收方法论（对我会 020 教训的同构印证）

Round 112"强证据规则"：文件存在不是证据、绿色测试不是证据（除非覆盖 requirement）、source 修改不是 runtime 证据。Round 119 再进一步：Profile 是三层 Module（source → compiled artifact → active catalog），**验收必须跨三层 seam**——source 改了 ≠ artifact 编译了 ≠ active 运行时没被 user shadow 盖回旧版（走查实测：system source 已新、active artifact 仍含旧 simulator gate，"status=loaded"完全掩盖这一点）。与我会 020 抓 Flash 自测失实、019 验收查图片引用零缺失，是同一套验收哲学。

### 3. 停止条件文化

README Goal 带 Blocked stop condition（对不齐就停不做双状态源）、Round 119 把 user shadow 定为 stop condition（不许静默覆盖手改 profile）。系统性"何时必须停"是作者工作法的标配，与 autonovel 借鉴清单的"停止条件"同族。

### 4. 142 轮走查零 UI 易用性议题

全库检索 onboarding/新手/引导/审批 UI 等关键词：零命中（审批/收件箱仅作为技术实体出现在工具路由审计里）。**142 轮全部在架构/数据/契约层打转，没有一轮从"用户好不好用"走查**——"基建 >> 产品"画像（52:10）再添铁证：连走查本身都是技术向的。对照：我会 019 走查页 + 用户实测一天产出 43 条易用性弹药，这条赛道作者从未起跑。
