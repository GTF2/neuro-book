# 外部实践调研：AI 长篇写作与 fork 维护（2026-09-14）

> 目的：避免闭门造车。调研结论用于**修正写作宪法中不精确的条款**、**借用成熟设计**，以及**确认哪些是我们真正原创**。
> 本文件是调研记录（provenance），不是行为合同；被采纳的结论要落到 doctrine 或 standards。

## 一、AI 长篇写作：已有的轮子

### 1. StoryForge（最值得对照；MIT，673 stars，本地优先，中文）

架构与我们高度同构，且在几个环上比我们成熟：

| StoryForge 机制 | 我们的对应物 | 差距/可借 |
|---|---|---|
| Context Gateway「先目录、后按需读取」+ 来源清单（Context Manifest / Source Manifest） | 建议读取 + World Engine 查询 | 我们**缺"实际用了哪些来源"的回执**；这正好是"事后校验"的取证基础 |
| 候选 → 作者确认 → `adopt()` → **回读验证** → 验收回执 | canon commit / 拍板落库 | 我们缺**回读验证 + 回执**（写进 World Engine 后回读核对） |
| **章后整理**：正文采纳后提出状态变化候选，作者逐项确认，偏差进**未来影响分析** | 事后校验 + 推翻留痕 | 我们缺**未来影响分析**：已确认历史稳定，受影响的下游规划（Promise/Scene/帧）标记待处理 |
| 世界引擎：语义快照 + **不可变世界版本** + 快照隔离 | World Engine 事件溯源（slices/patch） | 我们模型更强（可补写过去），但缺**版本冻结/派生世界**概念 |
| Skill + Run Contract 统一底座；节点模式与分步骤模式共享同一批 Skill | workflow + skill 资产 | 方向一致，可参考其"同一 Skill 两种编排"的复用方式 |
| 三种注册表数据治理：`CONTEXT_SOURCES`（读什么）/ `FIELD_REGISTRY`+`AdoptionSchema`（怎么校验写回）/ `PROJECT_TABLES`（导出/导入/删除生命周期） | DTO + reference + 目录合同 | 我们缺统一的"写回校验注册表"；评审清单可收敛到此形状 |
| 成熟度显式分级（正式入口 vs 预览）+ 承诺↔测试对照表 | PROJECT-STATUS / Spec 成熟度 | 同源做法 |

**它没有的东西**：没有关键帧概念；没有"事后校验、不事前告知"的方法论主张（它是"事前给足资料 + 事后整理"的稳健路线）。

### 2. 其它开源（中文圈为主）

`墨枢`（大纲/章纲/人物/世界观/时间线/RAG）、`NovelForge`、`Show Me The Story`、`Webnovel Writer`（基于 Claude Code）——**共同范式都是「总纲 → 卷纲 → 章纲 → 逐章生成」+ 设定库 + 时间线 + 检索**。

结论：**"章纲"是行业共识产物**。我们的 Scene 相当于章纲，但没有"章纲对象"的显式地位（brief 由 Scene 编译而来）。

### 3. 商业产品

Novelcrafter（codex 设定库 + 场景级 beats）、Sudowrite Story Engine（Braindump → Outline → **Beats** → Draft）。
两者都验证了「**节拍驱动生成**」。我们的 Promise beats 与之同源（仓库注释亦提到 storyforge 措辞）。

### 4. 学术界

- **Re3**（递归重提示 + 修订）与 **DOC**（Detailed Outline Control）：DOC 的两个组件是
  **① 详细大纲**（把大纲展开成细粒度细节再写）与 **② 实体状态追踪 + commit**，
  在长程连贯性上显著优于 Re3。
- **Dramatron**（DeepMind）：层级式剧本生成（premise → characters → beats → dialogue）。

**对我们的两点意义**：

1. **DOC 的"②实体状态追踪 + commit"≈ 我们的 World Engine + 关键帧**，说明这条路被学术验证过。
2. **DOC 的"①详细大纲"看似与宪法第二条（不给 writer 大纲）冲突**——见下面"需要修正的条款"。

## 二、叙事方法论：不要自造词汇

我们此前用"欲望 / 阻力 / 代价"描述帧的张力，其实**经典写作理论早有标准形式化**：

- **Swain 的 Scene/Sequel**：`Scene = Goal（目标）→ Conflict（冲突）→ Disaster（灾难）`；
  `Sequel = Reaction（反应）→ Dilemma（困境）→ Decision（决定）`。
- **Story Grid 的 Story Event** 五要素、**Save the Cat** 的 beat sheet 属同一族。

代码里 `StorySceneOutcomeType`（`yes_but` / `no_and` …）本身就是这一族的判断（"Yes, but"）。

**建议**：帧与场景的张力槽位直接采用 Swain 词汇，不自造术语；人写帧时填 `Goal / Conflict / Disaster`（或 `Reaction / Dilemma / Decision`），与既有 `outcomeType` 对齐。

## 三、需要作者批准的宪法修正候选

**宪法第二条（大纲≠切片）当前的表述过于绝对**：DOC 的实验显示"给模型更细的大纲"能显著提升连贯性，
而我们的实验显示"给 writer 意图级信息"会写出报告味。两者可以同时成立——差别在**粒度与层面**：

| 类型 | 例子 | 证据 | 应否进 writer 上下文 |
|---|---|---|---|
| **事实级细节** | 谁在场、发生什么、世界状态、不可逆变化 | DOC 详细大纲；我们的关键帧实验（可读性变强） | **应当给** |
| **意图级因果链** | 结局、意义、"必须隐瞒/只能暗示"、本章目标与落点 | 我们的对照实验（TOLD 组报告味） | **不应给** |

**建议修正**：第二条精确化为「**禁止意图级因果链，允许事实级细节**」。这解释了为什么关键帧有效（它是事实级细节），
也解释了为什么信息控制前置无效（它是意图级指令）。此修正须所有者批准后写入宪法。

## 四、我们真正原创的部分（诚实评估）

在本次检索范围内**未见同构**：

1. **"人只写不可逆状态变化帧，帧间补间交给模型"** 作为工作法（最接近的是 beat/章纲驱动，但 beat 不强调"不可逆"）。
2. **事后校验、不事前告知** 作为方法论主张（行业实践是"事前给足 + 事后整理"，我们刻意反其道）。
3. **回撞校验**：把"帧声明的不可逆变化"作为**逐条可比对的校验标的**（StoryForge 的章后整理是"模型提候选给人确认"，不是"拿声明去撞正文"）。

未见同构 ≠ 不存在；上述是我们的差异化赌注，需要继续用对照实验检验。

## 六、fork 维护的调研结论

GitHub 官方社区讨论（#153608）是**新手级**：只覆盖 `fetch + merge/rebase + push`、UI Sync、Actions 定时同步；
**未覆盖 `rerere`**，也未处理"fork 上有多个自定义分支"的情况——评论里正有人反映标准做法在这种情况下失效。

我们已有的 [`../standards/fork-upstream-sync.md`](../standards/fork-upstream-sync.md) 比它更具体；本次补充两条：
**启用 `git rerere`**（上游会反复动同一区域，尤其已决定保留的 83 文件 UI 定制）与**逐分支同步**
（UI Sync 只处理默认分支）。
