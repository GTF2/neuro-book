## 三、沉淀下来的打法（方法论，跨项目可用）

1. **看图选择工作法**：用户只在选择题模式下产出最高质量——参照物+编号标注+场景切换器+意见导出，把"形容"变"指认"，形容误差被图吸收。
2. **产出三步前置**（用户点名立规）：点名对口技能真调用 → 并行只读勘察（子代理分头摸资产/约束/惯例）→ 计划先行再动笔。违反=返工。
3. **工作流统一拓扑**：N 路并行勘察 → 总编/聚类 → 双设计师对撞+裁判合成 → 并行施工 → 独立验收+分版修复循环（≤2 轮）→ 发布。子代理 15-20 个、带出处防编造、只读约束写进 persona。
4. **闲时军团**：不依赖用户决策的预生产（预产图纸/组件/词表）全部塞闲时队列，醒来即用零等待；闲时任务口令三保险（触发即建 workflow/完整模型名防歧义/编译错修到跑通禁止手动降级）。
5. **组件宪法**：视觉语言以"可打回条款"形式固化（禁原生 select/按钮必带容器/选中线 2px 均匀/底部栏一体/展开缩进），所有产出物按宪法验收。
6. **口令自包含**：截图指代必须转译成代码定位（文件:行号）再下单，执行窗口零看图零猜测。
7. **对账纪律**：测试数必带基座 commit+替换/新增分列；报数与实测矛盾必点名翻案（R2 误报案、028 错报案均为正面处置样本）。

## 五、发布失败专项复盘（二队/广度版同病）

**现象**：两个 run 七个 phase 全 done、几十个子代理千万 token 的活全部完成，最后 `artifact.file: 'xxx' does not exist` 判 errored——但文件后来都在磁盘上（时序：发布跑在施工员写盘完成之前）。

**根因**：脚本信任了"子代理返回=文件落盘"，发布与写盘之间没有存在性验证；catch 补救里第二次发布未验证也未兜底，失败直接裸奔成 DriverError。

**立规（三个窗口全部适用；第 2 条 2026-09-22 一日两度翻案，现为终版）**：
1. 施工类子代理的 ask 必须以"写完用 ls/读回验证文件存在且非空，返回绝对路径"收尾——把落盘验证压进子代理职责（子代理的 Bash 走 shell，ls 可用）；
2. **发布段不设任何预检（终版）**。一案：`world.run("ls")` 在 Windows spawn 不走 shell、无 ls.exe，ENOENT 判整 run errored（首跑 504 万 token 施工全完成后死于发布段）。二案：改 `files.glob` 精确路径预检，工作流运行层五连误报"不在盘上"（文件实在盘上、run 外 snippet 测同一调用全正常），误打回补救员白烧 1418 万 token 且四件产物被简化任务书覆盖。结论：预检这层保险的故障率已超过它防的风险——整个删掉，发布只信 `artifact.file` 自身+双层 try 兜底。**连坐铁律：world/files 验证逻辑的任何改动，先 EvalWorkflowSnippet 实测再进脚本**；
3. catch 分支的兜底发布也要 try 包裹，最终失败降级为 log+把路径写进 return——**发布失败不得判整个 run 死刑**（活儿已完成就是完成了）。errored/stopped 后修脚本走 AmendWorkflow 复用缓存（不动的 ask 按名+字节匹配零 token 导入，只重跑病灶段）。
