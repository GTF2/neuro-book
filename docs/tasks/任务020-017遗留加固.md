## 目标

完成任务017 审合时登记的两项遗留加固（BOARD 历史决议 2026-09-20 三单审合条目）：

1. **删除/移动类端点缺少 `.nbook` 保留路径拦截**——017 的 `assertNotReservedWorkspaceWritePath` 只接入了写端点（`writeWorkspaceTextFile`）与上传三路（`normalizeUploadPath`），创建/移动/删除通路仍可触及 `.nbook/` 系统目录。
2. **Windows 路径尾点规约问题**——保留名比对是纯字符串口径，而 Win32 打开路径时会剥离段尾的点与空格（`.nbook.` 实际命中 `.nbook`），JS `path.resolve` 不做该规约，尾点变体可绕过拦截（实测 `path.resolve('C:/tmp/proj', '.nbook./x.ts')` 输出原样保留 `.nbook.`）。

## 做了什么

改动 2 文件 +70/-5（commit `8627a769`）：

**① 变更函数全量接入拦截**（`workspace-files.ts`）：`assertNotReservedWorkspaceWritePath` 接入 5 个此前未拦的变更函数——

- `createWorkspaceFile`（create-file 端点）
- `createWorkspaceDirectory`（create-directory 端点与 CLI `nbook node new`）
- `createWorkspaceContentState`（CLI `nbook node state`）
- `renameWorkspacePath`（rename 端点；源+目标都拦——移入等于写入系统目录，移出等于抽走系统文件）
- `deleteWorkspacePath`（delete 端点）

接入在函数层而非端点层，对齐 017 拦 `writeWorkspaceTextFile` 的既有模式；所有端点都经 tracked 层薄包装落在这 5 个函数上，一次覆盖 HTTP 与 CLI 全部调用面。已核验无内部合法调用者传 `.nbook` 路径（workspace-archive/project-file-index 等只用纯函数；`convertWorkspaceFileToDirectory` 源被 `isWorkspaceContentScopePath` 限制在 manuscript/lorebook 内，不可达 `.nbook`，无需接入）。

**② 尾点规约加固**（同一函数）：保留名比对前先剥离段尾的点与空格（`segment.replace(/[. ]+$/u, "")`）再比对 `.nbook`，口径对齐 `normalizeProjectRoot` 的 `[. ]$` 先例（project-identity.ts:191）。只收紧保留名判定，不新增业务路径拒绝规则（非保留名的尾点段如 `foo./bar.md` 行为不变）。

## 遗留问题

- 拦截合同只覆盖 `.nbook` 段名；更深的路径规约面（8.3 短名、ADS 冒号语法等）由 containment 真实路径检查兜底，未额外展开——超出"两项小加固"范围，如需成体系收口建议归前线定夺。
- `foo./bar.md` 类非保留名尾点段：Win32 会规约到 `foo/bar.md`，字符串层名字与实际落盘名存在差异。这是行为坑不是安全洞（对齐 `normalizeProjectRoot` 只在项目根层拒绝尾点的先例），未新增拒绝规则。
