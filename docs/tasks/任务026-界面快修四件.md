### ③ "未保存"徽章疑案——已定性并修复

**定性（三选一命中第一项：dirty 判断逻辑问题）**

原判定 `isFrontmatterDirty = 重组文本 !== 磁盘原始字节`。重组函数 `renderMarkdownDocument` 硬编码 LF 行尾 + frontmatter `trimEnd` + `---` 后固定补一个空行，只要磁盘文件是 CRLF 行尾、frontmatter 尾部有空行、或 `---` 后空行数≠1，**打开即字节不等 → 误报"未保存"**。Windows 下 CRLF 文件几乎必现，与"初始打开即显示"吻合。

排查过程中同时核实了另外两条链路并排除：`saveCurrentFile` 保存后 `loadWorkspaceTree()` 只替换节点元数据不动正文；编辑器防抖 flush 只在有未结算输入时上报，且编辑器失焦时不排 pending，"表单编辑→点保存"路径 flush 为 no-op，不构成覆盖。

**修复**

`workspace-frontmatter-profile.ts` 新增文本版四函数（组件内三段重复私有实现一并收敛进模块）：

- `splitWorkspaceMarkdownDocument`：按围栏切分，frontmatter 保真原文，**正文剥前导空行**
- `joinWorkspaceMarkdownDocument`：固定补回一个空行重组
- 两者构成**幂等规范化**（手算推演过每轮 +1 空行的不幂等坑，靠剥/补平衡消除）
- `normalizeWorkspaceMarkdownDocument` = split∘join

dirty 判定改为：磁盘态与编辑态**各过同一管道再比较**。行为闭环：

- 无变更（含一切格式差异）→ 不显示 ✓
- 真编辑 frontmatter → 显示 ✓
- 保存成功 → 落盘内容幂等，徽章消失 ✓
- 无变更文件不会被重写落盘（dirty=false 时保存禁用），磁盘原格式保持不动 ✓

## 执行偏差披露

1. **volume 的来源与口径**：代码里文件树标签原本直显 `node.entryType` 原值，volume 是用户工作区自定的 frontmatter type（lorebook 类型集合只有 location/character/item/rule/note）。已按指令翻"卷"，并做了**未知类型回退原值**的兜底（自定类型不再被吞）。
2. **③的修复范围只到徽章判定层**：排查中确认存在一条理论上的"正文编辑器防抖输入在保存时覆盖表单修改"竞态（TipTap 只装 body、frontmatter 存组件副本），但触发需要编辑器有未结算输入且失焦即结算，"表单编辑→保存"路径实际不触发；若用户实测遇到"改完保存后修改丢失"，那是另一层问题，建议另行立案。
3. **文件保存格式副作用**：修复后一旦真实编辑并保存，文件会规范化落盘（LF、围栏后恰好一个空行）；无编辑的文件永不重写。这是规范化比较的必然结果，对写作数据无损。
4. **en 复数文案**：`{count} words/items` 未做 vue-i18n 复数分支（1 items 这类边缘不优雅）；中文为主界面，快修不值得引入复数模板。

6. **Frontmatter 区块标签保留英文**：词表通用口径 API/JSON/YAML/Schema 保留，Frontmatter 属同域技术术语且任务点名只翻 FILE/MANUSCRIPT；如需一并中文化归第二批。
