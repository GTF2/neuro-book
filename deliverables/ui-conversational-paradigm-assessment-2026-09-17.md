## TL;DR

## TL;DR

**一句话结论：「主编对话式创作」这个愿景，基建完成度比直觉高得多——聊天驱动复杂操作的交互件（审批/表单/队列/模式切换/checklist）已全部存在，「聊天为主界面」的形态开关（agent 布局模式）也已存在；真正的缺口是三个「翻译层」：AI 产出的中间结构（大纲方案/章节列表）只会以 markdown 文本呈现、创作进度（写到哪章/brief 是否 ready）用户不可见、新会话没有主动开场白。愿景不是要新建一套东西，而是要把已建的引擎接上对话这个「方向盘」。**

但同时要诚实说清一个张力：**「仅通过聊天驱动」与产品已建成的差异化能力（四账本/World Engine 工作台）不是替代关系，是双形态关系**——聊天是「驱动层」，账本是「可查看层」。全部砍掉面板去迁就极简，等于把 Motor 砍了迁就自动挡（详见维度四）。

## 一、维度一：当前 UI 是否体现简洁原则

### 1.1 先回答「是否体现简洁原则」——用实测数据说话

并行会话已做的实测评审（`EDITOR-REVIEW.md`，Playwright 驱动真实浏览器量测）给出了可数的答案：

| 指标 | 实测值 | 判定 |
|---|---|---|
| 打开一章后可见按钮数 | **Agent 面板关 18 个 / 开 37 个** | ❌ 打开 AI 一个动作，可点对象翻倍 |
| 同一标题在屏出现次数 | **4 次**（标签/树行/H1/详情） | ⚠️ 已部分修（详情面板改路径单行） |
| 稿面正文行宽（Agent 开） | **676px** | ⚠️ 主角被邻居挤压 |
| 首屏挂载的 Dialog/Panel 组件 | **14 个** | ❌ 按「能力清单」而非「下一步决定」组织 |
| 活动栏常驻图标 | **6–7 个** | ⚠️ 分层已有，但写作型与配置型同权 |

**根因诊断（SIMPLIFICATION.md 已给出，我认可并引用）**：「界面是按能力清单组织的，不是按作者下一步要决定什么组织的」——四层能力（写正文/管设定/看运行/改配置）平铺同一层级。

**已经落地的收敛**（并行会话，均已提交）：稿面专注模式（非当前段 28% 不透明度）、界面简洁档（quiet/full）、活动栏按「写作时用/配置时用」分层、frontmatter 卡片退成配角、Agent 空态改发射台、稿面位置感状态行。

### 1.2 增量判断：从「对话式创作」视角看，简洁有第二个维度

上面全是**静态布局**层面的简洁。但「主编对话式」愿景提出了一个**动态维度**：

> **界面的复杂度应该随创作阶段变化——灵感期只需要一个聊天框，搭建期才需要结构视图，写作期回到纯稿面。**

现状是反着的：无论用户在哪个阶段，14 个面板全部挂载待命。一个「刚打开软件想聊灵感的用户」和「写到 200 章要查承诺账本的用户」看到的是**同一屏**。

**应精简/隐藏/延后的具体清单**（按用户进入产品的时序排）：

| 阶段 | 应该看到的 | 应隐藏/延后的 |
|---|---|---|
| 第一次进入（无项目） | 新建 / 打开示例书 / **和 AI 聊（目前缺失）** | 一切面板——现在空态之外的工作台结构对新人无意义 |
| 灵感期 | 聊天 + AI 引导提问 | 文件树、四账本、World Engine、历史——全部延后到「确定开书」时才出现 |
| 搭建期 | 聊天 + **中间产物的结构化确认卡**（目前只有 markdown） | 独立的手工建文件入口（AI 代建，人工只需确认） |
| 写作期 | 纯稿面 + 专注模式 + Inline AI | 聊天收进侧栏（一键唤回） |
| 回顾期 | 四账本 / 历史收件箱 / 扫 AI 味 | —— |

这个「复杂度阶梯」正是渐进披露（NN/g）在创作流程上的应用：**每个阶段只披露该阶段要做的决定**。

## 二、维度二：对话式创作流程的完整设计

### 2.1 现状盘点：对话式流程的「引擎」已存在，「方向盘」接了一半

代码级核实结论（侦察报告，带文件定位）：

| 环节 | 基建现状 |
|---|---|
| 阶段路由 | ✅ `novel-guide` SKILL 有「阶段判断速查」：说不清→灵感探索；缺设定→novel-setup 从缺的阶段进入；讨论/写章→novel-writing。**已注入 leader 系统提示** |
| 搭建引导 | ✅ novel-setup 四阶段各建 checklist 逐步推进、**阶段间需用户确认**、收尾汇报已建内容+占位清单 |
| 聊天中完成复杂操作 | ✅✅ 审批卡（tool_approval）、问卷卡（request_user_input）、**LowCodeForm 结构化表单**（9 种字段）、follow-up 队列（排队/忽略/投递）、运行中 steer 引导 |
| 会话管理 | ✅ 会话列表 + 分支树 |
| 「聊天为主界面」形态 | ✅ **agent 布局模式已存在**（`layoutMode: "ide"|"agent"`，agent 模式下聊天是中央主工作区+会话侧栏） |
| 模式安全 | ✅ 三模式（讨论/计划/正常）+ 写操作审批（本轮安全整改补全了 bash/sql/world/variable 标记） |

**三个真正的缺口**：

1. **新会话零引导**——新建会话不注入任何 assistant 首条消息，agent 只在用户首次发言后回应。「跟主编聊天」的第一步现在需要用户自己想开场白。
2. **中间产物只有 markdown 一条路**——AI 搭建大纲/章节列表时，方案以 markdown 文本呈现（GFM 表格可用）；没有「方案确认卡」这种结构化交互件。用户确认一个 12 章大纲 = 读一坨文本然后打字说「可以」。
3. **创作进度不可见**——leader 派 writer 写第 N 章，用户只能看到 writer 会话的状态点（running/waiting），**看不到在写哪章、brief 是否 ready**；`get_chapter_writer_brief` 的状态机（ready/needs_plot/needs_world_anchor）只存在于工具返回的文本里。

### 2.2 完整流程设计（开篇构思 → 搭建架构 → 章节续写）

以「主编聊天」的口吻设计全链路，**每个阶段的对话状态衔接**用「主编的话术 / 界面该出现什么 / 用户做什么」三栏表达：

**阶段一：开篇构思（对应 novel-idea-exploration）**
- 主编话术（首条主动开场白，目前空白）：*「想写点什么？随便聊聊就行——一个画面、一个人物、一种情绪都可以，我帮你把它捏成故事的形状。」*
- 界面：**只有聊天**（agent 布局模式）。
- 衔接：AI 判断灵感成熟 → 主动问「要不要开书？」→ 用户点头 → **阶段二**。关键：此时才出现「新建项目」动作，而非让用户先去建项目再来聊。

**阶段二：搭建架构（novel-setup 四阶段 + 定位/世界书/角色/World Engine）**
- 主编话术：*「开书之前我需要几样东西，一样一样来，每样你确认了我再继续。」*（checklist 机制已有）
- 界面：聊天 + **方案确认卡**（缺口 2 的解法）：AI 产出的设定/大纲以卡片呈现——可逐项 ✓/✗/改，而不是读 markdown 打字回复。参照 NovelCrafter 的「聊天产物一键转 Codex 条目」：**聊出来的设定直接落 lorebook，用户一次确认**。
- 衔接：四阶段 checklist 走完 → AI 汇报「已建内容 + 占位清单」（机制已有）→ 用户确认 → **阶段三**。

**阶段三：章节续写（novel-writing 循环）**
- 主编话术（每章循环的固定开场）：*「第 N 章要写什么？」* → 讨论剧情（讨论模式不动稿）→ 用户拍板 → 切正常模式 → AI 编 brief → 派 writer。
- 界面：**写作期 = 稿面为主角**（ide 布局 + 专注模式），聊天收侧栏；**进度条**（缺口 3 的解法）：writer 运行时侧栏显示「第 N 章 · brief ready · 正在写 · 流式预览」，点击可展开。
- 衔接：writer 交付 → leader 评审（写后结算表，P2-12 已拍板做）→ **「定稿」按钮**（P2-11 已拍板 B：自动跑一致性审计出报告）→ 用户看审计报告决定改或定 → 回到「第 N+1 章要写什么」。
- **每章用户只需要做三个动作**：说本章要什么、看结算+审计、点定稿。

**跨阶段状态衔接的机制总结**：阶段判断由 novel-guide 路由（已有）；阶段推进由 checklist + 用户确认（已有）；**缺的是每个阶段切换时界面形态跟着切换**（阶段一纯聊天 → 阶段三稿面为主）——这就是维度一说的「复杂度阶梯」。

### 2.3 竞品形态参照

**四大参照的交互形态事实**（PM 补充调研 + 主理人交叉核实，均来自官方文档/README/评测）：

| | 形态结构 | 对「主编聊天」愿景的启示 |
|---|---|---|
| **SillyTavern** | 中央消息流 + 底部输入；但**顶部常驻九个控制面板**（Response/API/Formatting/World Info/User/Backgrounds/Extensions/Personas/Characters）；消息级操作极强（Swipe 换生成、单条 Include/Exclude 控制可见性、看本次 prompt 与 token 用量）；有移动端 | ⚠️ 纯对话核心也没能免掉面板——**复杂度没处安放时只能堆进侧栏**，印证维度四「不能只做对话」的判断 |
| **InkOS Studio Chat** | **核实到的最接近「一个对话入口驱动全流程」**：建书/写章/改状态/封面全部从 chat 发起；**重动作先弹「确认卡」，普通讨论直接回答不进工具执行**；生成物在聊天中预览并继续修改；forecast 2-5 条分支在 Chat 中横向比较 | ✅ H2「方案确认卡」的直接参照——「确认卡拦截重动作」这个交互模式已被它验证；⚠️ 但其审计/评估深度操作仍只有 CLI，Studio 章节列表页未核实 |
| **novelWriter** | 左窄栏 + 两/三栏工作区；**Focus Mode（F8）隐藏除编辑器外全部 UI**；格式刻意阉割（无图片/链接/表格）；三种视图（Project Tree/Novel Tree/Novel Outline 大表格） | ✅ 「F8 一键退稿面」是极简档的成熟参照（我们的专注模式同思路）；其极简靠砍功能达成——不可照抄代价 |
| **NovelCrafter** | 编辑器 + Codex + 规划视图（网格/矩阵/大纲）+ Chat 的**多面板工作台**；Chat 消息区可选上下文范围（全书/幕/章/场景/codex 条目）；Scene Beats 四档控制 AI 自由度；prompt preview | ⚠️ 评测共识「学习曲线陡（AI 写作界的 Photoshop）」；**关键痛点：Codex 条目需手动创建，20+ 角色的书前期要花数小时**——这正是我们「AI 代建 + 用户确认」路线要消灭的成本 |

**一条对愿景最重要的横向事实**（PM 原话转录）：SillyTavern 和 NovelCrafter 都没有做到「纯聊天驱动一切」——前者保留九个控制面板，后者是多面板工作台里 chat 是一个入口而非唯一入口。**InkOS 的 Studio Chat 最接近，但其审阅/审计等深度操作仍需 CLI 或 Studio 页面。** 换句话说：**「仅聊天」在现有产品里没有任何一个完全实现**——我们的「聊天驱动 + 结构可见」双形态路线，恰好是这个空白位的合理填法。

### 2.4 一个必须诚实指出的边界

「AI 负责搭建整体架构、大纲与内容填充」在**冷启动**（新用户/新书）路径上是完整可行的——novel-setup 就是为此设计的。但**存量项目**（如 224 章真稿）走不了这条路：它们的结构已存在，AI 需要的是「逆向建档」（InkOS 的导入旧书逆向重建真相文件是同类思路），而我们的 worldAnchor 补齐工具（功能报告 P1-7）正是这个角色。**对话式愿景主要服务新路径，存量路径需要「导入 + 半自动补建」配套**——两件事都要做，不能只用一个。

## 三、维度三：界面与 AI 能力的衔接方式

### 3.1 功能入口：现状与「极简优先」的差距

现状的 AI 入口分布（已核实）：Agent 面板（主会话）、Inline AI 提示条（编辑器内选中即改，七任务）、「扫 AI 味」按钮（工具栏）、@ 触发菜单（composer 内可引用 skill/章节/lorebook）、模式切换（composer 按钮 + `/mode` 命令）。

**问题不是缺入口，是入口的「心智模型」不统一**：Agent 面板是「找 AI 帮忙」的心智，Inline AI 是「就地修改」的心智，llmlint 是「检查」的心智——三个入口对应三种用户意图，但视觉上没有这种区分引导。「极简优先」要求入口收敛为**一个心智**：**所有 AI 交互都是「跟主编说话」**，Inline AI 和扫描是「主编的快速指令」（不进会话的轻量路径）。

### 3.2 生成过程的反馈机制——已有件 + 缺口

**已有**（质量不低）：工具调用按工作类型聚合成 work block（explore/edit/command/database/web 六类）、运行阶段 8 态相位标签、审批/问卷卡、follow-up 队列面板（暂停原因人话展示）、模式切换消息。

**三个缺口**（按痛感排序）：

1. **长任务的进度感**——「AI 正在搭 12 章大纲」这类分钟级任务，现在只有相位标签。需要**任务级进度**（checklist 实时勾选可见——机制已有，差实时呈现）+ 可中断点明确（「确认后我才会继续」的视觉强调）。
2. **writer 的流式交付不可见**——writer 写正文时，用户若不切到 writer 会话就看不到任何产出。写作期用户最想看的就是「字在出来」。
3. **失败的可恢复性**——brief 不 ready（needs_plot/needs_world_anchor/needs_world_context）对用户是黑盒：不知道缺什么、不知道要做什么。应该翻译成主编的话：*「还差场景的世界锚点，我带你去补？」*

### 3.3 结果的呈现形式——分级呈现原则

按「结果的结构化程度」分三级呈现（这是对缺口「中间产物只有 markdown」的设计回答）：

| 级别 | 内容 | 呈现形式 | 现状 |
|---|---|---|---|
| L1 轻量 | 单点结果（改了一句、查了个设定） | 聊天内联卡片 | ✅ 已有（工具块） |
| L2 方案 | 结构化中间产物（大纲/章节列表/设定包） | **方案确认卡**：可逐项勾选/修改/要求重做，确认后落库 | ❌ 缺（现在只有 markdown） |
| L3 成品 | 章节正文 | 稿面流式预览 + 交付后直接进编辑器 | ⚠️ 半成品（流式在 writer 会话里，不在稿面） |

**L2 方案确认卡是整个「主编聊天」范式的枢纽交互件**——它把「AI 搭建、用户确认」从纯文本对话升级为结构化协作。NovelCrafter 的「聊天产物一键转 Codex」验证了这个方向（商业产品、15 万作者）。技术上我们的地基已存在：`request_user_input` 的选项卡 + LowCodeForm 表单就是同一族交互件，缺的是把「方案展示」也做成这类组件。

### 3.4 一个设计原则：反馈的「可关闭性」

极简优先的另一个要求：**AI 的反馈不强迫用户看**。37 个按钮的教训之一就是「一切信息常驻」。原则应是——运行状态常驻但极小（一个进度点），详情按需展开；方案卡出现时占据焦点（因为需要决策），决策后即收起归档（可从历史找回）。

## 四、维度四：可控性与灵活性的取舍

### 4.1 该方案的优势（真实、可验证的）

1. **门槛塌方式降低**——「上手门槛就是会打字」从宣传语变成架构事实：所有复杂操作（建结构/写设定/编排大纲）都被翻译成对话里的确认。对照竞品：AI 派全员要求 Node/Python 环境+配置（体检报告横向观察），传统派开箱即用但零生成——「对话式+本地优先」的结合位目前**没有占位者**。
2. **复杂度可管理**——AI 承担的不是「隐藏」复杂度而是「消化」复杂度：World Engine 初始化这种要懂 calendar/schema 的活，变成「主编问你五个问题」。跟「把面板藏进二级菜单」（复杂度只是被挪走）有本质区别。
3. **与产品安全架构天然咬合**——三模式 + 写操作审批 + 模式切换须用户点头，这些已有机制恰好构成「对话驱动」的安全边界：AI 能提议一切，但落库前都要过用户的确认点。

### 4.2 该方案的局限（同样真实）

1. **对话的表达上限**——「让主角在第 3 章比第 2 章更冷淡一点」用语言说得清；「把场景 12 的信息控制从『可暗示』改成『必须隐藏』但保留第 4 段的暗示」用聊天说就是折磨。**精细结构编辑天然属于表单/面板，不属于语言。**
2. **每章的对话轮次成本**——按 2.2 的设计，每章最少三轮（说需求/看结算/点定稿）。爽，但**不快**。写到 200 章的作者会想要「上一章的模式再来一遍」这种快捷路径（InkOS 的 `write next` 命中了这个需求，但那是全自动路线）。
3. **确认疲劳的风险（最需要警惕）**——如果每个阶段都要用户点头，而方案卡的信息量大到读不完，用户会进入「无脑点确认」模式。**这时候「用户批准」就退化成了橡皮图章**——宪法的人批准原则在形式上被满足、实质上被掏空。对策只能是：方案卡默认展示「摘要级」，展开才见细节；关键决策（推翻既有设定、不可逆操作）用更强的确认仪式。

### 4.3 潜在风险与对策

| 风险 | 机理 | 对策 |
|---|---|---|
| **AI 失误的结构性放大** | 用户没看到底层结构就确认了 AI 搭的架构——错误埋进 224 章的地基 | 方案确认卡必须带「查看原始结构」入口（一键跳到对应面板/文件）；写后结算表（P2-12）让每章新增事实透明 |
| **对话历史 = 流程记忆** | 换设备/清会话后，「主编知道的一切」丢失 | 对话只做驱动层，**一切已确认的事实必须落库**（lorebook/Plot/World Engine）——这本就是 Standard Flow 的设计，坚持「聊天不作为真相源」即可 |
| **极简之名下的功能迷失** | NovelCrafter 被用户评「useful features buried under multiple clicks」——复杂度转移≠复杂度消失 | 复杂度阶梯（维度一）+ 面板入口保留为「检查层」而非删除 |
| **双形态的维护成本** | 聊天路径和面板路径做同一件事，两套逻辑会漂移 | 聊天是「驱动层」、面板是「查看层」——**操作语义只有一份**（都在 server 工具/API 上），两套 UI 只是同一 API 的两个表皮 |

### 4.4 适用边界（明确圈出来）

- **适合**：新用户冷启动 / 新书从零搭建 / 网文节奏的持续产出（对话定方向+AI 填充）/ 对结构精细度要求低的创作阶段（初稿期）
- **不适合**：存量项目迁移（需要导入+半自动补建，见 2.4）/ 精细修订期（信息控制微调、承诺重排这类操作属于面板）/ 需要批量结构性操作的场景（一次性改 20 章的卷结构）

**核心裁决（一句话）**：不要把「对话式」做成「只能对话」——**聊天是方向盘，面板是仪表盘；方向盘可以简化，仪表盘不能拆掉**。竞品里 SillyTavern 纯对话形态被评「学习曲线陡」恰恰因为复杂度没处安放只能堆进对话本身；NovelCrafter 双形态共存（Chat + Codex + 规划视图）验证了这条路。我们的差异化恰好是**第三条路：对话驱动 + 结构可见**——比 SillyTavern 多了书稿结构，比 NovelCrafter 多了动态世界状态与事后审计。

## 五、结论与改进清单（按优先级）

### 5.1 总结论

1. **「极简优先」已有一条并行轨道在跑**（视觉收敛：专注模式/简洁档/活动栏分层，均落地）——本报告补充的是另一条轨道：**交互范式的极简**（复杂度阶梯 + 对话驱动）。两条轨道正交，合起来才是完整的「极简优先」。
2. **「主编对话式创作」的引擎已建成**（阶段路由/checklist/审批/表单/队列/模式安全/agent 布局），**缺的是三个翻译层**（开场白/方案卡/进度可见）——愿景的落地成本比「从零建」低一个数量级。
3. **不要做「只能对话」**——聊天是方向盘，面板是仪表盘；对话驱动 + 结构可见是我们的差异化第三条路（SillyTavern 只有对话没有书稿结构，NovelCrafter 有双形态但没有动态世界状态与事后审计）。

### 5.2 改进清单（按优先级）

**高（直接决定愿景成立与否）**

| # | 事项 | 依据 | 成本 |
|---|---|---|---|
| H1 | **新会话主动开场白**：按项目状态生成主编第一句话（无项目→「想写点什么？」；有项目→「上次写到 N 章，今天继续？」） | 缺口 1（侦察核实：零引导）；「主编」人设的第一块砖 | 小 |

### 5.3 与既有工作的衔接（避免撞车）

- **并行会话的视觉工作**（纸墨/专注/简洁档）：正交，互不阻塞；复杂度阶梯的「写作期」形态会直接复用它的专注模式与 quiet 档
- **功能诊断报告的 P0 兑现层**（备份 UI/RAG 解禁/历史面板/全稿扫描）：全部保留——它们是「仪表盘」的一部分，对话范式不豁免它们
- **P2 已拍板决策**（10C 设定检索自动候选/11B 定稿自动审计/12 写后结算表）：恰好是 H2/H3/M1 的后端前提，方向已锁
- **行动 12（AgentChatSurface 拆分）**：H1–H3 都要动这个组件——建议拆分工程与 H1–H3 合并排期，行为锁（e2e 已建）保护下进行
