## TL;DR

**一句话结论：NeuroBook 的功能架构深度在开源同类中没有对手（动态世界状态 + 事实/意图分离 + 承诺记账均为独有），但「已建成」与「已通电」之间隔着一条 UI 入口的鸿沟——四个后端完备的能力前端无入口，224 章存量项目的世界锚点为零，创作链路八个环节里有五个断点。差距不在能力，在兑现。**

流程三大断点（详见第二节）：灵感探索无前端入口、备份入口隐蔽（安全功能不易被用户发现）、写后回补对用户是黑盒循环。

## 一、功能对比（六维度）

### 1.1 对比对象

七项目分四类（竞品事实由产品经理两轮核实——novelWriter 官方文档 tags/references 页、SillyTavern 官方 WorldInfo 文档、各项目 GitHub README 均已直接核验；主理人对 InkOS / SillyTavern 世界书 / AI_NovelGenerator 三大关键机制做了独立交叉核实。star 数均为 2026 年 8-9 月第三方快照，**标注「未精确核实」处不做数字断言**）：

**传统写作组织工具（无 AI）**

- **novelWriter**（约 2-3k★，极活跃，v26.2 / 2026-09）——Python/Qt 桌面写作组织器。特色（官方文档核实）：**双层标签体系**——`@tag` 定义（笔记标题下声明，项目内唯一，按 Characters/Plot/Locations/Timeline/Object/Entity 七类根文件夹定语义）+ `@pov / @char / @plot / @location / @mention` 引用（写在场景文档头部）；**@mention 专门标记「提及但未出场」，官方定位就是供事后一致性人工检查**；引用面板反向汇总（打开笔记列出引用它的全部场景）、导出 HTML 交叉引用变超链接、`% synopsis` 梗概不导出正文、引用不存在标签可右键自动建笔记。本质：纯文本里做了一套「轻量结构化事实层」，靠人肉维护、无 AI。短板：无 AI、无中文排版优化。
- **manuskript**（约 3k★ 量级【未精确核实】，缓慢维护，0.17.0 / 2025-06）——雪花法写作工具。特色：雪花法 assistant（一句话 premise → 一段 → 全文摘要逐层扩写）；角色页签表单式档案；多条剧情线（每线含摘要/挑战/目标/结果，reference 字段把章节场景挂到线）；Storyline 视图按剧情线分道可视化；大纲双形态（层级 Outliner + 索引卡片可拖拽）。短板：技术栈老、无 AI。
- **Quoll Writer**（star 未核实，**实质停滞**：最后提交 2025-05，v3 自 2020 年「nearly finished」至今未发）——Java 桌面。特色：对象模型（QCharacters/QObject/ResearchObject 可挂任意 NamedObject）+ 自动可配置备份 + 全操作审计日志。**⚠️ 其「剧情板」传闻未核实**（README 与可达资料无证据，官网不可达），不采信。

**LLM 时代全自动长篇框架**

- **AI_NovelGenerator**（约 5.5-6k★，**维护不稳**：作者 2025-09 宣布无力维护、重构版在 dev 分支未完成）——Python GUI 全自动多章生成。核心机制（README 核实）：四步流水线（设定工坊→目录→草稿→**定稿**）；**「定稿」是一次原子状态更新**——同时写 global_summary.txt、character_state.txt、plot_arcs.txt 并把本章入向量库；向量检索回顾剧情；可选「一致性审校」（只报告不自动改）；五类任务各配不同模型的路由。短板：全自动无人环、状态是无 schema 的 txt、依赖安装劝退新手、维护风险高。
- **InkOS**（Narcooo/inkos，约 9.5k★【2026-09 博客快照，未精确核实】，极活跃，MIT→AGPL，2026-03 立项仅 5 个月到 v1.8.0）——中文网文向「故事创作 AI Agent 系统」，CLI + TUI + Studio Web 三端。核心机制（README 直接核实，本项目最强竞品）：
  - **五 Agent 编辑部**：建筑师（建 story_bible.md 世界观 + book_rules.md 创作规则）→ 写手 → 连续性审计员 → 修订员（**Spot-Fix 定点修复**而非整章重写，默认只自动修 1 轮）→ 文风工程师（统计指纹仿写）
  - **一致性四层**：① **7 个真相文件**（world_state / character_matrix / resource_ledger 资源账本 / **hook_board 伏笔钩子**（起始章节、状态、预期回收时间）/ chapter_summaries / subplot_board / emotional_arcs），每章写完自动更新；② **37 维连续性审计**（角色记忆/物资连续/伏笔回收/大纲偏离/节奏/情感弧线…）+ 定点修订循环；③ 三层记忆（Zod schema 状态 JSON + 人类可读 md 投影 + SQLite FTS5/BM25 时序检索）；④ 状态写入安全（LLM 输出 JSON delta → immutable 更新 → 结构校验，坏数据直接拒绝）
  - **版本管理**：每章自动状态快照、`write rewrite` 可回滚任意章节、**安全章节工作区（正文+状态+伏笔先校验再原子提交，杜绝「状态推进了正文没落盘」）**、文件锁防并发
  - 其他：`inkos forecast` 剧情多线推演（写前生成 2-5 条隔离分支供横向比较）、`inkos up` 守护进程后台写章（关键问题暂停留审+通知）、去 AI 味三件套（词汇疲劳表/禁用句式/anti-detect 改写）、导入旧书逆向重建真相文件、同人模式（canon/au/ooc/cp + 信息边界管控）、15 个 SKILL.md 能力包
  - 短板：起步仅半年、配置格式不稳定（README 自述）、无编辑器级人机协作、无决策记录/信息控制类结构、生态依赖多
- **Long-Novel-GPT**（约 1.1-1.2k★，**停更**：最后更新 2025-11）——三层自上而下扩写 Agent（大纲→章节→剧情→正文，各层可切分多线程并行）；自动检索相关正文片段进 prompt，修改正文时同步更新剧情纲要；拆书模式导入现有小说提取人物关系。主打「一键生成百万字」。短板：无编辑器级协作、停更。

**世界观/角色卡体系**

- **SillyTavern**（约 2.8-3.3 万★，极活跃，AGPL）——LLM 前端，角色卡+世界书生态。**世界书（World Info）触发机制**（官方文档核实，参数体系极全）：条目三型（🔵常驻无条件注入 / 🟢关键词触发 / 🔗向量匹配按嵌入相似度）；主副关键词四逻辑（AND_ANY/AND_ALL/NOT_ANY/NOT_ALL）+ Regex 混用；Insertion Order 与七档插入位置（可插到聊天记录指定深度 @Depth）；触发概率 %、同组互斥加权随机、Sticky 粘滞 / Cooldown 冷却 / Delay 延迟（以消息数为单位）；**递归扫描**（条目内容可连锁唤醒其它条目，可限步数、可做逐层揭示）；全局 Scan Depth + Context% token 预算（常驻优先、直接提及优先于递归）。它解决的问题是「50 个 NPC / 20 个地点 / 10 个魔法系统不爆上下文」。短板：为 RP 对话设计、无大纲/章节/承诺概念，一致性是会话级注入而非书稿级闭环。

**通用知识库**：Obsidian + 插件生态常被用于写作素材管理——与我们「数据自持」同路线，不展开。

### 1.2 逐维度分析

#### 维度一：世界观 / 设定管理

**我们的实况（代码级核实）**：
- **World Engine**：Subject / Slice / Patch 三层 + Instant 时间轴，是世界动态状态的唯一真相源（`server/world-engine/`，UI 入口 `WorldEngineWorkbenchDialog.vue`）——开源同类中**唯一的动态状态引擎**，其余全部是静态设定文件
- **Lorebook（世界书）**：纯文件化（Markdown + frontmatter：title/type/status/aliases/tags/summary），数据自持、任意编辑器可开
- **场景世界锚点（worldAnchor）**：场景可绑定时间/subjects/地点，是「剧情与世界状态咬合」的关键机制
- **问题**：224 章存量项目**全部场景 worldAnchor 为空**（`status=needs_world_anchor`）——引擎建成了，老项目没通电；`selectedLorebookEntryId`（`stores/novel-ide.ts:218`）是死状态，只在 `:406` 被置 null、从不赋真值

**主流做法**：SillyTavern 世界书按关键词自动触发注入；manuskript 雪花法分步展开设定；novelWriter 纯文件夹 + key 词标签自动汇总。

**判断**：**架构领先一到两代**（动态 vs 静态），但「可用性兑现」落后——竞品的功能用户开箱即用，我们的 World Engine 需要走完 novel-setup 四阶段才能建立，存量项目迁移成本高。

#### 维度二：角色管理

**我们的实况**：角色 = `lorebook/character/**/index.md` 文件（无独立数据表），搜索/增删改有完整面板；特色是**重量级角色卡工作坊 skill**（20/24/80/200 问法）与 SillyTavern 角色卡三段式导入。

**主流做法**：SillyTavern 角色卡生态（社区卡片量大）；manuskript 有角色弧光/动机的结构化字段。

**判断**：**基础持平，缺一块**：角色的「结构化追踪」（弧光阶段、出场章节统计、与线程的关联）没有面板——角色在承诺账本里只是场景的在场者，没有自己的成长账本。

#### 维度三：大纲与章节规划

**我们的实况**：这是**差异化最强**的维度。四账本——线程规划 / **承诺账本（伏笔埋设-推进-兑现全程记账，写到目标章自动进写作指令）** / 决策记录（决策当场记档、风险必填、推翻留痕）/ 关键帧；外加 Act/Chapter/Scene 三层结构、场景信息控制四字段（读者已知/主角已知/必须隐藏/可暗示）。契诃夫之枪由软件提醒。

**主流做法**：manuskript 雪花法大纲、Quoll Writer 剧情板、novelWriter 分卷文件夹——均为**静态大纲组织**，无承诺/决策/信息控制概念。

**判断**：**明显领先**。「承诺账本」在七个对比对象中没有同类——最近的是 InkOS 的 hook_board（伏笔钩子带起始章节/状态/预期回收），但那是**文件快照**级追踪，不是 beat 级（埋设→推进→兑现）全程记账；决策记录与信息控制四字段在全部对比对象中均无对应物。

#### 维度四：文本生成与续写

**我们的实况**：leader/writer 分工链（leader 管剧情与调度，writer 只写正文、上下文只含事实级切片）；**writer brief** 编译门槛（status 非 ready 不动笔）；Inline AI 七任务（chat/rewrite/polish/expand/condense/continue_after/bridge，选中即改流式预览）；三模式（讨论/计划/正常，切换须用户点头）；讨论/计划模式下写操作自动挂审批。

**主流做法**：AI_NovelGenerator / Long-Novel-GPT 是**全自动无人值守 pipeline**（一键出全书，人不在环里）；InkOS 走人机协作。

**判断**：**架构深度领先，傻瓜路径缺失**。全自动竞品牺牲的是可控性（事实漂移、不可干预），我们的取舍相反——这是定位差异而非差距；但「链路深度」带来的复杂度，目前只有对话一个消化口。

#### 维度五：上下文一致性维护

**我们的实况**：
- 理念层**独有**：宪法级「事实/意图分离」（writer 动笔前只拿事实切片，意图级内容全部转为事后评审项）+「事后校验不事前告知」
- 工具层：World Engine 状态查询（writer 只读）、retrieval 由 leader 人工选径、llmlint 事后扫 AI 味（360 规则、236 文件 1.48s）、RAG 后端完备（sqlite-vec）**但前端被契约测试锁死不挂载**
- **缺口**：「设定不吃书」没有自动化检查——只有文档约定 + 承诺账本人工核对；一致性维护的人工环节占比高

**主流做法**：SillyTavern 关键词扫描自动注入（无人工选径）；AI_NovelGenerator 向量检索 + 自动一致性校验流水线。

**判断**：**理念领先，自动化落后**。竞品把一致性做成了「自动流程」，我们做成了「纪律 + 人工核对」——后者质量上限高、下限也低（取决于人是否执行）。

#### 维度六：版本与存档管理

**我们的实况**：架构是全场最深的——nb-history 事件溯源 + 内容寻址快照 + 操作日志；历史收件箱（分组待审 + Monaco diff + 接受/还原）；备份后端（归档/密钥环/恢复，本轮刚完成安全加固：剔除密钥 + 端点鉴权）。**但**：备份 UI 已挂在 Passport 账户面板，入口位置隐蔽，不在作者会主动查找的设置/项目工作流中；收件箱组件注释自认「时间线/删除找回面板留给下一任务」。

**主流做法**：PM 横向观察——**版本与存档是全梯队的共性弱项**，多数项目只有文件级快照甚至没有。

**判断**：**架构最深、用户可见面最窄**——「做了用户看不见」的典型。半成品 UI 是唯一短板，架构无对手。

## 二、流程诊断：灵感 → 设定 → 大纲 → 正文 → 润色全链路

以产品自己定义的 Standard Flow 八步（`novel-writing-workflow.md:20-29`）为轴，逐步对照「产品定义」与「用户实际体验」：

| 步骤 | 产品定义 | 用户实际体验 | 判定 |
|---|---|---|---|
| 1 灵感探索 | `novel-idea-exploration` skill，从模糊灵感整理成故事雏形 | **无前端入口**——它只存在于 agent 会话里，新用户不知道这条路存在；README 宣传的主链第一步在前端没有实体 | ❌ **断点** |
| 2 项目检查 | 确认 Workspace / 目标章节 / World Engine 初始化状态 | 新建项目 = title+summary 就地表单提交，**无向导**；初始化状态对用户不可见（要问 agent） | ❌ **断点** |
| 3 Canon 准备 | 稳定设定进 lorebook，走 novel-setup 阶段一~三 | 手动建文件或对话内完成，**无进度可视**；lorebook 详情面板的死状态（selectedLorebookEntryId 从不赋值） | ⚠️ **不顺畅** |
| 4 World Engine init | 阶段四建 calendar/schema/锚点/开局状态 | 老项目（224 章）**0 锚点**——这条路存量项目从没走过，World Engine 实际没通电 | ❌ **断点（存量）** |
| 5 剧情规划 | 剧情初步设计 → 落库 → 细化 → 更新 Plot | 四账本完整，默认 tab 已改承诺账本 | ✅ 通畅 |
| 6 Retrieval | leader 手选 `entries[].path` 进 writer payload | 对用户**完全透明**（黑盒）；RAG 检查器后端有、前端锁死，看不到检索过程与依据 | ⚠️ **不透明** |
| 7 章节写作 | brief 编译，status≠ready 时先补 Plot/Anchor/Context 再编译 | 「不 ready → 补什么 → 再编译」的循环对用户是黑盒；写一章要跨多轮对话 | ⚠️ **黑盒循环** |
| 8 写后回补 | leader 评审，新事实回拍板落库补 World Engine | 流程有定义但**无界面引导**——用户要知道「该回补了」并主动开对话；「设定不吃书」靠人工 | ❌ **断点（引导缺失）** |

**润色环节**（链路终点）：llmlint 编辑器入口（单文件抽屉）+ Inline AI 七任务 ✅ 通畅；但**全稿批量扫描无入口**（CLI 实测 236 文件 1.48s，app 只有单文件）。

**重复操作盘点**：
- 每章都要完整走「设计→落库→brief→写作→评审→回补」，**没有「续写上一章」的快捷路径**（第二章起每章成本不变）
- Inline AI 与 Agent 会话是**两套上下文体系**，同一份稿子的润色状态不互通
- 写后回补与下一章的剧情设计有重叠动作（都要过一遍 World Engine 状态）

**结构性观察**：八个断点里，**没有一个是「能力缺失」**——全部是「能力建成了、入口/引导没跟上」。这与功能对比的结论一致：差距在兑现层。

## 三、借鉴清单

按「值得引入」排序，每条注明来源、理由、与宪法红线的关系。**分两类：工程/交互类（可直接引入）与形态决策类（宪法边界，只列选项不替作者定）。**

### A. 工程/交互类——可直接引入

**1. InkOS 的「安全章节工作区」原子提交（最高优先借鉴）**
- 机制：写章时把「正文 + 状态更新 + 伏笔变更」放进隔离工作区，**校验通过后一次性原子提交**——杜绝「状态推进了、正文没落盘」的半途状态。
- 理由：这正面命中我们的**写后回补断点**（步骤 8）——当前 leader 评审后「回拍板落库环节补 World Engine」是多次分散写入，中途失败就留下不一致。我们的事件溯源（nb-history）比它深，但**没有把它组织成原子事务**。
- 兼容性：纯工程层，不触写作方法论。
- 落点建议：在 leader 的写后回补环节，把「正文落盘 + World Patch + Promise beat 更新」包成一个可回滚的提交单元（nb-history 的内容寻址快照天然支持）。

**2. InkOS 的 hook_board（伏笔钩子板）字段设计**
- 机制：每个伏笔带「起始章节、当前状态、**预期回收时间**」——审计维度会主动检查「距预期回收已过 N 章仍未兑现」。
- 理由：我们的承诺账本已有 plant/payoff beat 与 deadlineChapterId，但**没有「逾期未兑现」的主动提醒视图**；README 承诺的「写到目标章自动进入写作指令」只做了一半（进指令），「过期未响枪」的警示没做。
- 兼容性：账本已有数据结构，加一个过滤视图即可。

**3. AI_NovelGenerator 的「定稿 = 原子状态更新」交互概念**
- 机制：用户点一次「定稿」，系统同时更新摘要、角色状态、向量库、剧情要点——**状态更新是定稿的副作用，不是用户的后续 chores**。
- 理由：我们的「写后回补」要求用户知道该回补并主动开对话——把这个变成「定稿」按钮的自动编排（leader 收尾动作打包），用户心智从「我要记得回补」变成「我点定稿」。
- 兼容性：流程编排层。**但回补的具体内容确认权仍在人**（符合宪法「人批准」精神），只是把「发起」自动化。

**4. novelWriter 的 @mention（「提及但未出场」标记）**
- 机制：场景文档里 `@mention: 某角色` 专门标记「本章提到了但没出场」——**官方定位就是供事后一致性人工检查**。
- 理由：这跟我们「事后校验」路线天然同构。我们的场景只有「在场角色」（worldAnchor.subjects）没有「提及」层；而「提了没出场」正是伏笔/信息控制的常见载体。
- 兼容性：纯数据字段 + 视图，无方法论争议。

**5. llmlint 全稿扫描入口（自家能力，补入口即可）**
- 事实：CLI 实测 236 文件 / 1.48s；app 侧只有单文件抽屉。竞品 InkOS 的审计是全书级的。
- 理由：这是**零新建能力、纯补 UI**的一条——把 `check` 的目录递归模式暴露成「扫描全稿」按钮。

**6. novelWriter 的引用反向面板**
- 机制：打开任一 lorebook 条目，列出**引用它的全部场景**，导出时变交叉链接。
- 理由：我们的 lorebook 条目有 aliases/tags，但没有任何「谁在用我」视图——「设定不吃书」的人工核对缺这个抓手。

### B. 形态决策类——宪法边界，待 GTF 拍板（只列选项）

**7. SillyTavern 世界书的触发参数体系**
- 机制全貌：蓝灯常驻 / 绿灯关键词 / 向量匹配三型；四逻辑组合；插入位置七档 + 深度；触发概率、Sticky/Cooldown；递归扫描；Token 预算分配（常驻 > 直接命中 > 递归）。
- 价值：参数体系是十年 RP 社区打磨出来的「上下文注入控制面板」，任何要做「按需取设定」的系统都绕不开这套词汇表。
- ⚠️ **红线关系**：关键词自动注入本质是「**事前告知**」路线——宪法第五条裁决的是「事后校验，不事前告知」。**引入与否是形态决策，只有你能定。** 若引入，合理落点是 leader 的 retrieval 环节（给 leader 的选径加自动化选项，而非直接喂 writer——这样不违反「writer 只拿事实切片」）。

**8. InkOS 的写前自检表 / 写后结算表**
- 机制：写手动笔前输出自检表（确认已读真相文件），写完输出结算表（本章改变了什么）。
- ⚠️ **红线关系**：写前自检表是事前路线（但不进 writer 上下文，只是 writer 的内部纪律，可能兼容）；写后结算表是**事后路线，完全兼容**——我们的 brief 编译已要求 status=ready，结算表相当于给「写后回补」一个结构化输入。**建议只评估结算表**。

**9. InkOS 的 Spot-Fix 定点修复**
- 机制：审计不过时只修出问题的段落，不重写全章，且默认只自动修 1 轮。
- ⚠️ **红线关系**：修改正文是写作动作。我们 llmlint 当前**只读不写回**是有意设计（改稿权在人）。**自动改写正文不在授权范围内引入**；但「人工批准后执行定点修复」（Inline AI 已有 rewrite 单任务能力，缺的是「按审计命中定位」的联动）可以评估。
