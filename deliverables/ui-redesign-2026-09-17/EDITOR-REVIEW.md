## 0. 为什么重做这次评审

前几轮我对界面的判断都建立在**空状态截图**（欢迎页）上。那评的是首页，不是主场景。

**主场景是「打开一章、正在写」的那一屏。** 这份评审只评那一屏。

方法：Playwright + 本机已下载的 Chromium，驱动真实浏览器进入工作台、展开文件树、打开 `manuscript/000-opening/index.md`，然后截图 + 量测 `getComputedStyle` 的实际值。

## 1. 结论先行

**病灶不是「元素多」，是「元素之间没有层级」。**

打开一章后，屏幕上同时存在四个平级的面板区，每一个都有自己的 header 和按钮排：

```
活动栏(48) │ 文件树(~420) │ 稿面 │ Agent 面板(~390)
                              ↑ 主角，但看上去和邻居一样重
```

量测证据：

| 指标 | Agent 面板关闭 | Agent 面板打开 |
|---|---|---|
| 屏幕上可见按钮数 | **18** | **37** |
| 稿面宽度 | 908px | 724px |
| 正文行宽 | 860px | 676px |

**打开 Agent 面板这一个动作，把屏幕上的可点对象翻了一倍。** 而稿面在视觉上并没有因此变得更"重"或更"亮"——它只是变窄了。

## 2. 逐条发现

### F1 · 标题在同一屏出现 4 次（可数）

量测：文本 `开篇：蓝梓与芥末` 在一次渲染里有 **4 处可见**：

| 位置 | 出现形式 | 坐标 |
|---|---|---|
| 顶部标签 | `开篇：蓝梓与芥末` | y=11 |
| 正文 H1 | 章标题 | y=144 |
| 左栏文件树行 | 树节点 | y=261 |
| 左栏详情面板 | `标题 / 开篇：蓝梓与芥末` | y=693 |

四处各有理由（标签是"当前打开"，树是"在哪个位置"，H1 是"文档内容"，详情是"这一章的身份"），**合起来是同一句话说了四遍**。眼睛在四个地方读到同样的信息，就学不会"哪里该看"。

→ 建议（未实施）：树行与详情面板去重；顶部标签在只有单标签时不必显示文件名（正文 H1 已经说了）。

### F2 · 稿面第一眼是元数据，不是正文（已修）

打开一章，正文上方第一眼是一张**带描边、带底色**的卡片，内容是一行等宽字体的 YAML：

```
> title: 开篇：蓝梓与芥末        [✎] [🗑]
```

右侧还常驻一个**红色垃圾桶**（删除 frontmatter），随时待命。

这是写作工具里最"工程感"的一处：读者打开一章想看故事，先看到的是一条 YAML 和一个删除按钮。

→ **已修**（提交 `35a0890d`）：折叠态平时不描边不填底、摘要行降到 `--text-muted`、操作区（含删除）平时透明且不可点，hover / focus-within 才浮出。见 `C1-frontmatter-quiet.png` 与 `C2-frontmatter-hover.png`。

### F3 · 专注模式的初始判定是错的（已修）

这是我上一轮交付的功能，在真实界面里第一眼就是坏的：

**开启后，标题独立保持全色，正文 131 个块全部降到 28% 不透明度。** 观感是"文字被禁用了"，而不是"专注模式开着"——比不开还糟。见 `A2-light-focus.png`（修复前）。

根因：ProseMirror 打开文档时默认把选区放在文档起点（也就是章标题里），标题是 textblock，于是被判定为"当前块"。

→ **已修**（提交 `337b8493`）：标题排除在"当前块"之外，顺延到它后面第一个正文块。修复后 `B1-light-focus-fixed.png`：标题作为结构退后，正文第一段被点亮。点正文中段，高亮正确跟随（`B2-light-focus-mid.png`）。

> 这条证明了本文件夹存在的必要性：**读代码完全看不出问题，静态截图也看不出**。只有让它在真实浏览器里跑起来、点一下工具栏按钮，才会看到"整篇变灰"。

### F4 · 工具栏 6 个入口全是纯图标

稿面顶部一排：分段控件（富文本/源码）、准星（专注写作）、对话气泡（评论视图）、魔法棒（扫 AI 味）、更多。**没有一个有文字标签。**

`title` 属性只在 hover 时出现——**鼠标悬停不算视觉引导**，它是隐藏式帮助。用户要在 6 个抽象图标里猜哪个是"专注写作"。

→ 建议（未实施）：把"扫 AI 味""评论视图"这类低频项收进"更多"，常驻只留当前视图切换 + 专注写作；或给常驻项加文字短标签（空间足够：这一排目前只占约 180px）。

### F5 · Agent 面板的空态是死路，不是发射台（已修）

打开 Agent 面板（状态：有可用对话但未选中），中间是：

> 请选择一个对话
> 当前实例还有可用对话，但没有可靠的上次选择。请从对话列表中选择。

**两行说明文字，零个可点对象。** 唯一的按钮在底部输入区、相距约 500px；而此刻输入框是**禁用**的，所以整屏无处可去。说明叫用户"从对话列表中选择"，却不给能选的地方。

> 注意区分：另一个空态（已选会话、还没有消息）**不是**这个问题——那时输入框可用，composer 本身就是发射台。要修的只有"未选中"这一个。

→ **已修**（提交 `b860d989`）：补「新建对话」（主）+「会话列表」（次）两个起点，正好对应正文那句话的两个出口。同时把底部 composer 状态条从指令式（"请选择一个对话后继续。"）改成陈述式（"未选中对话，输入已停用。"）——**让页面级空态负责"去哪里"，控件级说明负责"为什么这里是灰的"**，不再同一屏说两遍。空态图标也从 `status-warning` 的橙底改回中性："未选择"不是错误状态，而橙底会把注意力吸到一个没有动作的图标上。

见 `empty/W2-agent-empty.png`（改前）与 `empty/W3-agent-empty-after.png`（改后）。

### F6 · 主题：`light` 不是为写作工具设计的

`A1-light-default.png`（当前使用）与 `A3-sepia-default.png` 对比，观感差距不需要解释：

- `light` 是**纯白 + Tailwind 默认灰阶**（`--bg-panel #ffffff`、`--border-color #e5e7eb`、`--text-main #111827`）——一套框架默认值，不是设计决策
- `sepia` 是暖纸底 + 赭石橙（`#fdf6e3` / `#d97743`），跟正文的"纸"这一形态同源

而这个产品**原本的默认主题就是 `sepia`**（`resolve-theme.ts` 的 `DEFAULT_THEME_ID`）。现在窗口用的是 `light`。

→ 建议（未实施，零成本）：改回 `sepia`。暗色场景推荐 `tokyo-night`（最克制的蓝灰）。8 套对比见 `themes/00-overview.png`。

### F7 · 左栏详情面板（**经查证不是问题**）

初看像是"左栏被切成两半，下半是只读的统计与元数据"，很冗。

查证后撤回：`WorkspaceFileDetailPanel` **可关闭（`×`）也可拖拽调高**（`:height` / `@update:height`），是上下文相关的面板，不是强制常驻的 chrome。

## 4. 下一步建议（按影响面排序）

**① 让稿面成为唯一的高对比区域** —— **已完成（`aa424195` 机制 + `710655fb` 覆盖面）**

角色映射层的 `--panel-surface` 现在有 5 个消费方：主界面左栏工具面板 + 剧情大纲面板外壳 + 剧情工作台侧栏 + 承诺账本 + RAG 的 Subject 列表。简洁档一开，这些导航 chrome 全部退场。

判断标准（唯一一条，已写成契约测试）：
> **「让你走到某处」的面板用 `--panel-surface`；「让你读/写」的面板用 `--bg-panel`。**

**位置不是判据**——三个检查器里有两个在右侧，但它们是"当前对象的属性/元数据"视图，属「读」，所以不换；Agent 对话面同理（它和稿面同属"纸"）；设置对话框内的分区也不换（对话框自身就是一个独立的内容面）。

契约测试 `panel-surface-consumers.contract.test.ts` 锁死的是**「内容面误用」这个方向**——误用不报错，只是简洁档把该保持亮面的区域一起退掉，现象看起来仅像"档位效果比预期强"，极难归因。反向（新面板忘了归类）不拦：默认用 `--bg-panel` 是安全默认。

**② Agent 面板空态给可点起点**（F5）—— **已完成（`b860d989`）**

页面级空态负责"去哪里"，控件级状态条负责"为什么这里是灰的"。这条分工确立后，同一屏不再有两句指令。

**两条查证后撤回的判断（记在明处）**：
- 欢迎页那行「还没有打开的文件…」**本来就是 button**（点了进 `manuscript/`），不是死路；它已有 hover 反馈与虚线边框表示空槽，所以未改。
- hero 的「打开文件树」与左栏已展开的文件树确有重复，但判断"左栏此刻是否可见"需要跨组件传状态，成本大于收益，未做。

**未改但已记录**：`unselected` 仍用 `tone: "warning"`（黄底）。按语义"未选择"不该是警告，但 `tone` 是 8 个状态分支共用的体系级决策，单改一个分支会造成体系内不一致——要做就整组一起做。

**③ 标题去重**（F1）

成本中（牵动树行、详情面板、顶部标签三处），需要产品判断。**建议放在①之后**——层级建立起来之后，"哪里该显示标题"会自然有答案；现在做等于拍脑袋。

**④ 稿面工具栏收噪音**（F4）

成本低，但优先级低于①：图标不可发现是"找不到功能"，而①解决的是"没有重心"——后者才是用户原话里的问题。

## 4.5 途中发现的 repo 级问题：`/NN` 透明度后缀被静默丢弃

**不在本轮修复范围，但影响面很大，必须记下来。**

写 `bg-[var(--bg-panel)]/78` 这类"任意值 + 透明度后缀"时，UnoCSS **不应用这个透明度**。它把带后缀和不带后缀合并成同一条规则：

```css
/* 浏览器里枚举出的真实生成 CSS */
.bg-\[var\(--bg-panel\)\], .bg-\[var\(--bg-panel\)\]\/35, …\/45, …\/50, …\/60, …\/85, …\/88, …\/90 { background-color: var(--bg-panel); }
.bg-\[var\(--panel-surface\)\], .bg-\[var\(--panel-surface\)\]\/78 { background-color: var(--panel-surface); }
```

**一律是全不透明。** 而全仓这个写法约百处（`bg-[var(--bg-input)]/40` 16 处、`bg-[var(--toolbar-bg)]/95` 10 处……），也就是说：**这些地方的实际不透明度都比作者写的更高。**

**怎么发现的**：为了确认「角色 token 替换是零变化」，在真实浏览器里枚举 `document.styleSheets` 的 `cssRules`（dev 模式下 UnoCSS 的输出由 JS 注入，`curl` 抓不到）。证据是上面的规则原文，不是推断。

**为什么它在本轮无害**：既然后缀本来就是失效的，把变量名从 `--bg-panel` 换成 `--panel-surface`（标准档下两者同值）就**必然保持一致**。所以 ① 的零变化结论不受影响。

**一个仍在的疑点**（如实记录）：`/92`、`/65`、`/95` 这几种后缀**连规则都没生成**（探针读到透明），而 `/35 /45 /50 /60 /78 /85 /88 /90` 生成了。同为 `var()` 任意值、同一种写法，行为不一致，原因未查明。若是"dev 模式按需生成"所致，那么在干净的构建里应当都存在——但**没有验证构建产物**。

**建议**：要做就整仓一起做——要么给这类半透明意图改用显式的 `bg-[color-mix(in_srgb,var(--x)_78%,transparent)]`（无歧义），要么去掉后缀接受全不透明。**不要零散地改一两处**，那只会让不一致更难查。
