### J2 · 新用户第一次拿到 AI 写的一章

**用户故事**：我想看看 AI 能替我写成什么样。

**完整路径**：J1 全部 + 配置 Provider（外部依赖）：
1. 打开设置（Activity Bar 底部齿轮，`NovelIdeActivityBar.vue:368`）
2. 找到 Provider 配置页

4. 保存
5. 回 IDE，点 Agent 面板图标（`workbench-chrome.ts:78-80`）
6. 输入意图
7. 发送
8. 等

**可测量 DoD**：

| 指标 | 目标 | 判定方式 |
| --- | --- | --- |
| 从"想看 AI 写"到正文区出现第一段 AI 文本 | **≤ 10 分钟** | 录屏计时 |
| 其中「配置 Provider」耗时 | ≤ 4 分钟 | 分段计时 |
| Provider 表单字段数 | ≤ 4 个必填 | 数字段 |
| 第一次调用失败时，报错信息里出现 HTTP 状态码 / JSON / 堆栈 | **0 次** | 触发一次错误 Key 验证 |
| 需要离开 NeuroBook 去做的事 | ≤ 1 件（注册拿 Key， unavoidable） | 记录 |

**失败定义**：
- 超过 10 分钟
- 任何一步需要翻文档站
- API Key 填完后**没有任何成功反馈**（静默保存 = 用户不知道成没成）
- 第一次调用失败时给用户看 `401 Unauthorized` 而不是"你的 API Key 不对，去xx重新复制一次"

**当前状态**：🔴 **未达标，且风险最高**。这条 Journey 里有一个**完全不受你控制的外部环节**（注册 OpenAI/DeepSeek 账号、充值、拿 Key）。对一个"编程小白"作者来说，这是整条链路最大的流失点。

**强烈建议（这是我最想说的一条）**：**做一条"零配置 Demo 通道"** —— 内置一个 NeuroBook 官方的免费额度代理（哪怕限 3 章 / 每天 20 次），让新用户**不配 Key 就能完整跑通 J2**。用户一旦看到自己那本书被 AI 写出来一章，配 Key 就不再是障碍而是顺理成章。这一步的转化率差异，是量级差异。
> 注：这需要评估成本与 AGPL 合规（代理服务算不算"通过网络提供服务"），不是拍脑袋就能上——但方向我认为是对的，值得你单独决策一次。

### 3.4 等待时间

代码可确认的：项目加载是 **6 个阶段**（`project-route-progress.ts:4-11`）：
```
preparing → opening-project → connecting-presence → syncing-project → loading-tree → restoring-content
```
UI 上会显示「第 N/6 步」（`zh-CN.ts:1762`）。

**"第 N/6 步"这个设计是好的**（让用户知道在动、还有多久），但**阶段名字暴露了不该暴露的东西**：`connecting-presence`（正在建立连接）和 `syncing-project`（正在同步作品信息）对一个本地单机用户来说，只会产生两个疑问："连到哪？""同步给谁？"——**而这恰恰是本地优先软件最不该让人怀疑的地方。**

**改法（一行 i18n 的事）**：
- `connectingPresence`: "正在建立连接" → **"正在打开作品数据"**
- `syncingProject`: "正在同步作品信息" → **"正在读取设定与正文"**

**实际耗时**：`PROJECT-STATUS.md` 与 `HANDOFF.md` 全文**没有任何一处记录冷启动耗时**。HANDOFF 只记了「dev server 10 秒就绪」（`HANDOFF.md:99`），那是服务器不是项目打开。

**建议**：把"冷开一部 224 章的书要多少秒"当作一个**必须被记录和守护的数字**（见 §5 dogfooding 的 A1 断言）。你连这个数字都不知道，就没法谈"打磨有没有进展"。

### 4.3 首屏实际给了用户什么

`NovelIdeActivityBar.vue` 的 10 个入口（`workbench-chrome.ts:66-85`）：

```
primary（5）  : home(书架) / files(文件) / characters(角色) / plot(剧情) / world(世界)
secondary（2）: trace(Trace Viewer) / history(历史收件箱)
agent-panel(1): AI 面板
footer（2）   : account(账户) / settings(设置)
```

**问题不是"10 个太多"（VS Code 也有 10 个），问题是"10 个全是等权的、且没有一个在替 README 说话"。**

一个从 README 点进来的用户，看到这 10 个图标，他的心理活动是：
> "这看起来像个编程用的 IDE。我的小说在哪？"

而一个纯图标 Activity Bar 有个致命问题：**图标无法承载产品主张**。`i-lucide-globe-2` 不会告诉用户"这个东西能告诉你三个月前哪个角色受了伤"。

**更糟的是首屏主区**：`ProjectPickerScreen.vue` 953 行里，主视觉是**书籍封面网格 + 封面上传/替换/清除 + 一套封面操作失败恢复状态机**（L356-608，约 250 行）+ **Session 迁移恢复区**（L143-205 + L784-835，约 160 行）。

**价值密度倒置**：首屏 410 行服务于"封面管理"和"数据迁移运维"，而服务于"四大能力"的行数是 **0**。

### 4.4 建议：哪个能力该在第一步被感知

**我的主张：第一步该被感知的是「承诺账本（伏笔）」，不是 World Engine。**

理由（这是产品判断，不是技术判断）：
- **World Engine 的价值是"不出错"** —— 但一个还没写过 100 章的新用户，**感受不到"吃书"的痛**。你向一个没痛的人卖止痛药，他不会买。World Engine 是**留存能力**，不是**获客能力**。
- **"我第 3 章埋的伏笔忘了填"是任何写过 3 章以上的人立刻能懂的痛** —— 而且它能在 **5 分钟内被完整演示**（埋一个 → 让它提醒你 → 兑现）。这是**获客能力**。
- **llmlint 排第二** —— "AI 味"是任何用过 ChatGPT 的人一眼能识别的东西，演示成本 30 秒，视觉冲击最强。它是**传播能力**（最适合做演示视频/GIF 的那个）。

排序：**获客（承诺账本）→ 传播（llmlint）→ 留存（World Engine）→ 转化（Agent 工作室）**。

### 4.5 三处具体改法

#### 改法一：空态即演示（最高优先级，一周内可做完）

**不要在新建书籍后给用户一个空白编辑器。**

改为**预置一本 3 章的微型示例书**（不是「第一章」占位符，是一个有血有肉的微型故事），并且这本书里**提前埋好**：
- 第 1 章：主角捡到一把枪（一个 Promise，目标章 = 第 3 章，**未兑现**）
- 第 3 章：正文里**故意带着 5 处典型 AI 味**（"首先…其次…"、"值得注意的是"、"在这个充满挑战的世界里"之类）

用户打开这本示例书，一眼看到：
- 剧情面板上一个红点：「**这把枪还没响**（目标：第 3 章）」
- 编辑器侧栏：「**检测到 5 处 AI 味**」→ 点开逐条高亮

**四大能力一次全感知，零配置，零学习。**

**为什么这个改动价值最大**：新用户的第一分钟决定了他会不会有第二分钟。现在的第一个是"空白页 + 十个螺丝孔"，改完是"一台正在工作的机器"。这是**同一个产品的两种命运**。

> 风险提示：示例书内容需要你自己写（不能 AI 生成，否则打脸）。3 章 × 800 字 = 2400 字，一个下午。这是**投入产出比最高的一天工作量**。

#### 改法二：Activity Bar 从 10 个收敛到 5 个 + 图标加文字

```
现在（10 个等权图标）
home / files / characters / plot / world / trace / history / agent / account / settings

改成（5 个 + 折叠）
文件 / 剧情 / 世界 / AI / （更多：trace、history、角色、账户、设置）
```

具体：
- `trace`（Trace Viewer）和 `history`（历史收件箱）是**运维/调试入口**，收进"更多"
  → 代码里**已经有 overflow 机制**（`resolveActivityBarSecondaryItems`，`workbench-chrome.ts:91`），现在只在"放不下"时用；改成**默认就把次要项塞进去**
- `characters`（角色）：角色在 README 里不是独立卖点，可并入文件或收进更多
- **Session 恢复整块移出首屏**（见 §3.2）
- 封面管理的 250 行代码保留（功能本身没问题），但**不占首屏主区**，降为卡片 hover 的次要操作（现在已经是 hover 才显示，OK）

**图标下面加两字标签**（Activity Bar 从 48px 加宽到 64px）。纯图标导航对"编程小白"作者是灾难。VS Code 能纯图标是因为它的用户是程序员，你的用户是小说作者。

#### 改法三：把 README 那 6 步做成首屏的进度条，或者从叙事里删掉

`README.md:108` 说：「默认写作主链：**灵感探索** → 项目与世界书初始化 → World Engine 建档 → 剧情规划与状态推进 → 章节写作 → 写后回补」。

**实证**：
```

（返回空）
$ grep -rln "灵感" packages/neuro-book/app/components/
packages/neuro-book/app/components/novel-ide/plot/tree/plot-tree.preview-data.ts   ← 只有假数据
```

**第一步「灵感探索」在前端代码里完全不存在。** README 在卖一个不存在的功能。

而且**整条 6 步链路在 UI 里没有任何阶段指示器** —— 用户永远不知道"我现在在第几步"。

**两个选择，你挑一个（我推荐 A）**：
- **A（推荐）**：把「灵感探索」从 README 叙事里删掉，主链改成 5 步，并把这 5 步做成首屏顶部一条细进度条，当前步高亮。**好处**：既是导航，又是产品主张的可视化，还顺手解决了"用户不知道下一步干嘛"。

## 5. Dogfooding 机制：把 224 章真稿变成产品资产

### 5.1 现状

**真稿存在**（实测 `%LOCALAPPDATA%\NeuroBook\data\workspace\xin-xiao-shuo\`）：
- `manuscript/` 下 **236 个 `index.md`**（224 章 + 卷目录）
- `lorebook/` 下 10 个分类（character / event / faction / instruction / item / location / note / system / world）
- `world-engine/`（calendar.ts + schema）
- 322 个场景 / 9 条线索（`PROJECT-STATUS.md:33`）

**但**：
- `HANDOFF.md:144` 和 `PROJECT-STATUS.md:33` 都只是**在文档里提了一句"有这么一部书"**
- **没有任何一条自动化断言在它上面跑**
- **没有任何一份历史基线记录"上周它长什么样"**
- `PROJECT-STATUS.md:90` 写着「下一阶段是 dogfooding」—— 列在"风险与验收缺口"里，作为**未来的事**，而不是**每周发生的事**

**一句话诊断**：224 章真稿现在是一件**展品**，不是一件**工具**。它被参观（写在文档里），没有被使用（跑在 CI 里）。

### 5.2 可执行的机制（6 条，按实施顺序）

#### 第 1 步：把真稿冻结成只读夹具（半天）

- 把 `xin-xiao-shuo` 复制成 `packages/neuro-book/test-fixtures/novel-224/`（压缩存储，或 git-lfs）
- **必须做匿名化**：人名/地名/组织名批量替换。理由有二：① AGPL 仓库公开，未发表作品直接进公开仓库有风险；② 匿名化后才能放心地把它用于任何测试
- **只读**：任何测试不得修改它；需要写盘的场景，复制到临时目录再跑
- 这一步做完，你就拥有了一个**全世界只有你有的资产**：一部真实的、224 章的、带完整 lorebook 和 world-engine 配置的长篇小说测试夹具。任何竞品想复现这个测试环境，都得先写 224 章。

#### 第 2 步：定义 6 条定时断言（每周跑，全部输出数字）

| ID | 断言 | 红线 | 抓的是什么 |
| --- | --- | --- | --- |
| **A1** | 冷开这部书到可编辑的耗时（跑 3 次取中位数） | 比上周 +20% | 性能回归（**这条同时补上了 §3.4 的数据空白**） |
| **A2** | 236 个 `index.md` 全部通过 `validateWorkspaceTree`，issue 数 | 必须 = 0 | 解析回归 |
| **A3** | 随机抽 5 章跑 `consistency-audit`，**撞错数必须 > 0** | = 0 时报警 | **检测器本身坏了**（真稿一定有可撞的错，一个都撞不出来说明检测器瞎了。这条最重要也最反直觉） |
| **A4** | 9 条线索的 Promise 状态分布快照（埋下/推进/兑现/逾期各多少） | 与上周 diff 只允许定义内的变化 | 承诺账本回归 |
| **A5** | 随机 10 章跑 llmlint，问题数分布（P50/P90） | 与上周漂移 > 30% 报警 | 规则集回归（360 条规则改一条就可能全盘漂移） |
| **A6** | 打开最长的那一章（第 N 章）到可编辑耗时 | 比上周 +20% | 大文件性能悬崖 |

**A3 值得单独解释**：这条断言的方向是**反的**——它期望"发现错误"。因为一部 224 章的真稿，一致性检查**理应**能撞出东西。如果某天它撞出 0 个错，不是你的书写得完美了，是**检测器坏了**。这类"期望失败"的断言是防止检测器静默失效的唯一办法。

#### 第 3 步：产物必须是「可 diff 的 JSON」，不是报告

每周产出 `dogfood-report-2026-09-17.json`：
```json
{
  "date": "2026-09-17",
  "fixture": "novel-224@sha256:...",
  "assertions": {
    "A1_open_ms": {"value": 4200, "delta_vs_last": "+3%", "status": "pass"},
    "A2_tree_issues": {"value": 0, "status": "pass"},
    "A3_consistency_hits": {"value": 7, "status": "pass", "note": ">0 才对"},
    "A4_promise_dist": {"planted": 12, "advanced": 8, "fulfilled": 4, "overdue": 3},
    "A5_llmlint_p50": {"value": 23, "delta_vs_last": "-12%", "status": "pass"},
    "A6_longest_chapter_ms": {"value": 1100, "status": "pass"}
  }
}
```
**进 git。人只看 diff。**

**关键设计约束**：**可 diff、有数字、无截图。**
- 截图人不会每周看
- 数字会自己说话
- 数字能进 git，能出 diff，能被 CI 断言

#### 第 4 步：CI 接线（半天）

新增 `.github/workflows/dogfood-weekly.yml`：
- 每周日 03:00 触发 + 手动触发
- 跑 `bun run dogfood:weekly`（复用已有的 `scripts/smoke/` 基础设施）
- 失败 → 自动开 issue 并 @ 你
- 成功 → 把 JSON commit 回仓库（这样历史基线就是 git history 本身，零额外存储）

> 注意：现有 `scripts/smoke/writing-workflow.ts`（`packages/neuro-book/scripts/smoke/`）**不能直接用**——它要求"dev server 已启动、Provider apiKey 已配置、用户手动提供 project"（该文件 L11-15 前提模式），是**手动脚本**不是 CI 资产。dogfood 脚本要另写，且**默认不依赖真实模型**（A1/A2/A4/A6 都是纯本地的；只有 A3/A5 需要模型，做成可选）。

#### 第 5 步：你每周只做一件事，10 分钟封顶

**打开 diff，对"变化是否符合预期"打勾或打叉。**

- 全绿 + 数字没大变 → 关掉，10 秒
- 有数字跳了 → 问自己一句"我上周改了什么导致它跳？"→ 想得通就打勾，想不通就打叉开 issue

**这是整个机制的设计核心**：作者的时间成本必须 ≤ 10 分钟/周。超过 10 分钟，第 3 周就会被放弃——这才是最常见的 dogfooding 死法。

#### 第 6 步（加分项）：把真稿变成对外资产

README 现在卖能力靠的是一张**对照表**（`README.md:42-48`）和截图。**没有一句真实文本。**

**建议**：从 224 章真稿里抽 3 章（去敏后），做成一个「真实效果」示例页：
- 左栏：同一章的 AI 直出（用通用聊天框写）
- 右栏：NeuroBook 产出（帧驱动 + 事后校验 + llmlint 过一遍）
- 下方：llmlint 在 AI 直出版上刷出的 N 条问题，逐条高亮

**这是转化率最高的一块缺失。** 你的目标用户（写长篇的人）对"能力矩阵表"免疫，但对"同一段文字的两种质感"毫无抵抗力——**因为这就是他们的日常生活。**

## 8. 评审员的一句话收尾

NeuroBook 最可惜的地方不是功能不够——**功能是过剩的**。最可惜的是：**你花了两年造的四个最贵的能力，用户打开软件的前 60 秒一个都看不见。**

修这个不需要新功能，需要的是把已经造好的东西**搬到用户眼前**。

**「体验打磨」这四个字，从今天起换成「J1–J5 五条 Journey 的数字有没有变好」。** 数字动了，就是有进展；数字没动，就是在原地转圈。这才是有终点的路。
